# 10. З чого починати

> Чернетка порядку робіт. Не оцінка строків — послідовність і ризики.

## Головна порада: спершу тонка нитка

Найбільша небезпека великого проєкту — зробити всі частини окремо, звести їх у
кінці й побачити, що вони не сходяться.

Тому перше, що варто зробити — **наскрізна тонка нитка**: один робот з **одного
кроку**, який проходить весь шлях:

```
Studio: створити робота з одним кроком «клікнути»
   ↓  опублікувати версію
   ↓  запустити на своїй машині
Desktop: справді клікнув
   ↓  лог повернувся
Studio: видно «виконано»
```

Некрасиво, без редактора, без бібліотеки елементів. Але як тільки це працює —
усі інтеграційні сюрпризи вже позаду, а далі йде нарощування.

## Порядок фаз

| Фаза | Що робимо | Чому саме тут |
|------|-----------|---------------|
| **0** | Моделі БД: `robots`, `robot_versions`, `machines`, `jobs`, `job_logs`, `robot_access`. Реєстрація машини. Юзерський вхід у веб + перевірки ролей | без цього не існує ані робота, ані місця, куди його слати |
| **1** | Каталог активностей + валідація при публікації + HTTP для Studio. Сюди ж — тип поля `secret` і сховище облікових даних (D20) | задає контракт, на який спираються решта фаз; секрети мають існувати **до** першого робота з логіном |
| **2** | **Executor**: інтерпретатор (змінні, `ForEach`, `If`, `TryCatch`) + провайдер `desktop-uia` | найбільша й найризикованіша частина |
| **3** | **Inspector** для `desktop-uia` + канал захоплення + знімок | без нього робота неможливо зібрати |
| **4** | **Studio UI**: редактор кроків, бібліотека елементів, форми з каталогу | найбільша частина фронту |
| **5** | Запуск і спостереження: Job, логи пачками, перегляд виконання | замикає цикл |
| **6** | Розклад запусків (D28) + чекліст машини для нічної роботи | дешево, а дає нічну роботу — головну цінність для бізнесу |
| **7** | Провайдер `office-com` | дешевший за браузер, а цінність висока |
| **8** | Провайдер `web-cdp` | фактично другий Inspector |

Після MVP: повний unattended на VM (D3b).

## Дрібна задача, яку варто зробити рано

**Перейменування у Face за D29** — поки фронту небагато. `Processes` → Роботи,
`Agents` → Машини, і далі за канонічним словником. Зараз це дешево; коли
екранів стане вдвічі більше, назви розповзуться по компонентах, типах і
константах.

## Ризики, які варто зняти рано

| Ризик | Коли перевіряти |
|-------|-----------------|
| **PyInstaller + comtypes** — UIA працює в розробці, падає у зібраному `.exe` | одразу після першого робочого прототипу провайдера, не перед релізом |
| **Реальна програма замість тестової** — 1С поводиться не так, як Блокнот | захопити елемент у справжній 1С якнайраніше |
| **Продуктивність обходу дерева** — великі вікна дають тисячі елементів | на реальному вікні, не на прикладі |
| **Тонка нитка не сходиться** | фаза 0–1, до того як написано багато коду |

## Що свідомо не робимо в MVP

- **повний** unattended на VM без залогіненого юзера (D3b) — нічний запуск на
  машині юзера при цьому є, див. [11-schedule.md](11-schedule.md)
- ротація паролів, історія використання креденшлів, зовнішні сховища секретів
- пошук по картинці (D7b)
- Word і Outlook — тільки Excel
- повноцінні вирази у полях (D6b)
- підтвердження машин адміном (D10)
