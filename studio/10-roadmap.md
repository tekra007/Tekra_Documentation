## Головна порада: спершу тонка нитка

Найбільша небезпека — зробити частини окремо, звести їх у кінці й побачити, що
вони не сходяться. А частин тепер пʼять: Face, Studio, RabbitMQ, оркестратор,
десктоп.

Тому перше — **наскрізна тонка нитка**: робот з **одного кроку** проходить увесь
шлях **через усі пʼять частин**:

```
Face ──HTTP──► Studio: створити робота, сценарій — сирий JSON з одного кроку «клікнути»
                  │ «Зберегти» → версія 1.1 + подія в outbox
                  ▼
               RabbitMQ
                  ▼
           Оркестратор: зареєстрував версію (перевірив хеш), записав аудит
                  │ подія «registered»
Face ──HTTP──► Оркестратор: запустити 1.1 у TEST на своїй машині
                  │ EXECUTION_ASSIGN
                  ▼
           Десктоп: справді клікнув → лог і результат
                  ▼
Face ◄──WS─── Оркестратор: видно «COMPLETED»
```

Некрасиво: без редактора, без Inspector, без погоджень. Але щойно це працює —
інтеграційні сюрпризи (брокер, outbox, токени між сервісами, WS) позаду, далі
лише нарощування.

**Чому аудит і outbox — одразу, а не потім.** Аудит пишеться в тій самій
транзакції, що й зміна (D41), а outbox — у тій самій транзакції, що й подія
(D67). Вбудувати це в кожну операцію з першого дня дешево; дописувати потім у
готовий код — дорого й з дірками.

## Що вирішити на старті фази 0

> 🟡 **Відкрито** (2026-10-05): рекомендації нижче ще не підтверджені — повернутись
> перед початком фази 0.

| Питання | Варіанти | Рекомендація |
|---------|----------|--------------|
| **Де живуть схеми повідомлень** брокера — їх читають обидва сервіси | окремий пакет `tekra-contracts` / копія в кожному репо + контрактний тест / один репо — власник | окремий пакет — схеми не розійдуться; вирішити перед першою подією |
| **Стек Studio-сервісу** | той самий, що в оркестраторі (FastAPI, SQLAlchemy async, Alembic) / інший | той самий — одна команда, одні звички |
| **Перехід токенів на пару ключів** зачіпає наявний вхід адмінів і десктопа | разом із фазою 0 / окремо раніше | разом, бо Studio без цього не перевірить токен |

## Ризики, які варто зняти рано

| Ризик | Коли перевіряти |
|-------|-----------------|
| **Outbox / inbox працюють неправильно** — дублікати, втрачені події, порядок | фаза 1: вимкнути оркестратор посеред «Зберегти», увімкнути — версія має доїхати рівно один раз |
| **Розмір повідомлення** — великий `definition` не влазить у ліміт RabbitMQ | фаза 1: найбільший реалістичний сценарій зі знімками елементів |
| **PyInstaller + comtypes** — UIA працює в розробці, падає в зібраному `.exe` | одразу після першого робочого провайдера, не перед релізом |
| **Реальна програма замість тестової** — 1С поводиться не так, як Блокнот | захопити елемент у справжній 1С якнайраніше |
| **Продуктивність обходу дерева** — великі вікна дають тисячі елементів | на реальному вікні, не на прикладі |
| **Список зʼєднань у памʼяті процесу** (`ConnectionManager`) — оркестратор не можна запускати в кількох копіях | не блокує MVP; знадобиться перед масштабуванням оркестратора |

## Що свідомо не робимо в MVP

- **повний** unattended на VM без залогіненого юзера (D3b) — нічний запуск на
  машині юзера при цьому є, див. [11-schedule.md](11-schedule.md);
- ротація паролів, історія використання креденшлів, зовнішні сховища секретів;
- пошук по картинці (D7b);
- Word і Outlook — тільки Excel;
- повноцінні вирази у полях (D6b);
- підтвердження машин адміном (D10);
- кластер RabbitMQ — у MVP один вузол (D67);
- окремий запуск компонента (D66).
