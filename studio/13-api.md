# 13. HTTP API для Studio

> Чернетка. Уточниться при реалізації.
> Що йде по WebSocket — у [09-protocol.md](09-protocol.md).

## Стиль, який наслідуємо

Він уже склався в проєкті, тому нові ендпоінти лягають так само:

- шляхи згруповані у фронті по доменах (`ROBOT_URLS`, `JOB_URLS`) — у сервісах
  не хардкодяться;
- ресурс у множині: `/robots`, `/jobs`, `/machines`;
- пагінована відповідь має вигляд
  `{ total_pages, current_page, pagination, items, counts }` — як у `GET /logs`.

## Що вже є і що з ним станеться

`routers/robot.py` існує вже зараз:

| Наявний ендпоінт | Доля |
|------------------|------|
| `GET /robots/user/{user_id}` | замінюється на `GET /robots` |
| `DELETE /robots/user/{user_id}/robot/{robot_id}` | замінюється на `DELETE /robots/{id}` |
| `POST .../start`, `.../pause`, `.../stop` | замінюються на `POST /jobs` і `POST /jobs/{id}/stop` |
| `POST .../schedule-robot` | замінюється на `/schedules` |
| `GET /robots/robot/{robot_id}/kpi` | рахується з `jobs` |

Прод-даних немає (робоча умова розділу), тому старі шляхи прибираються, а не
підтримуються паралельно (D14).

### Важлива зміна принципу

Наявні шляхи носять `user_id` **усередині URL**:
`/robots/user/{user_id}/robot/{robot_id}/start`.

Нові — ні. Організація і роль беруться **з токена**, а перевірка доступу
робиться на сервері за D25. Клієнт не називає, від чийого імені він діє.

### Ще одна зміна: розклад переїжджає на сервер

Сьогодні розклад живе **на десктопі**: `RobotScheduler` у `robot_layout.py` зі
своїм вікном налаштувань, а сервер лише проксіює команду по WebSocket. У БД
сервера розкладу немає взагалі.

Наслідки поточної схеми: розклад зникає при перевстановленні застосунку, адмін
не бачить, що і коли запускається в компанії, керувати з вебу нічим.

За D28 розклад стає серверною сутністю (`schedules`), а десктоп лише виконує
`Job`, які приходять.

## Каталог активностей

| Метод | Шлях | Що робить |
|-------|------|-----------|
| `GET` | `/activities` | увесь каталог (D2). Майже статика — кешується |

## Роботи

| Метод | Шлях | Що робить |
|-------|------|-----------|
| `GET` | `/robots` | список; фільтри: пошук, архівні, машина |
| `POST` | `/robots` | створити |
| `GET` | `/robots/{id}` | картка |
| `PATCH` | `/robots/{id}` | назва, опис |
| `PUT` | `/robots/{id}/draft` | зберегти чернетку сценарію |
| `POST` | `/robots/{id}/validate` | перевірити сценарій → `{ errors, warnings }` ([14-validation.md](14-validation.md)) |
| `POST` | `/robots/{id}/publish` | опублікувати версію → повертає версію |
| `POST` | `/robots/{id}/archive` | прибрати з очей |
| `DELETE` | `/robots/{id}` | видалити остаточно — **тільки `ADMIN`** (D25) |

### Версії

| Метод | Шлях | Що робить |
|-------|------|-----------|
| `GET` | `/robots/{id}/versions` | історія публікацій |
| `GET` | `/robots/{id}/versions/{versionId}` | конкретна версія зі сценарієм |
| `POST` | `/robots/{id}/versions/{versionId}/activate` | відкотитись на попередню |

### Доступ

| Метод | Шлях | Що робить |
|-------|------|-----------|
| `GET` | `/robots/{id}/access` | кому дозволено запускати |
| `POST` | `/robots/{id}/access` | дати доступ юзеру |
| `DELETE` | `/robots/{id}/access/{userId}` | забрати |

## Машини

| Метод | Шлях | Що робить |
|-------|------|-----------|
| `GET` | `/machines` | список: онлайн, версія агента, `capabilities` |
| `GET` | `/machines/{id}` | картка |
| `PATCH` | `/machines/{id}` | перейменувати |

Створення немає навмисно: машина зʼявляється сама, коли агент підключається
(D10).

## Запуски

| Метод | Шлях | Що робить |
|-------|------|-----------|
| `POST` | `/jobs` | запустити: `{ robot_id, machine_id, input }` |
| `GET` | `/jobs` | список; фільтри: робот, машина, статус, дата |
| `GET` | `/jobs/{id}` | картка запуску |
| `GET` | `/jobs/{id}/logs` | покрокові логи, пагіновано |
| `POST` | `/jobs/{id}/stop` | зупинити |

**Чому `POST /jobs`, а не `POST /robots/{id}/run`:** запуск — це не властивість
робота, а окремий обʼєкт зі своїм життям, статусом і логами. Ми його все одно
показуємо списком і фільтруємо. Тому створюємо його як звичайний ресурс.

У тілі можна передати `robot_id` (візьметься поточна опублікована версія) або
`robot_version_id` (конкретна — для перезапуску старої).

| `POST` | `/schedules` | створити |

## Облікові дані

| Метод | Шлях | Що робить |
|-------|------|-----------|
| `GET` | `/credentials` | список — **без секретів**, лише назва й логін |
| `POST` | `/credentials` | створити |
| `PATCH` | `/credentials/{id}` | назва, логін |
| `PUT` | `/credentials/{id}/secret` | змінити пароль |
| `DELETE` | `/credentials/{id}` | видалити |
| `GET` | `/credentials/{id}/usage` | які роботи ним користуються |

Пароль не повертається **жодним** ендпоінтом (D20). `usage` потрібен, щоб не
видалити те, чим користуються.

## Наскрізні правила

- організація й роль — **з токена**, ніколи з URL;
- права — за матрицею D25, перевіряються на сервері, а не хованням кнопок;
- усі списки пагіновані у форматі `GET /logs`;
- операції, що змінюють стан, видимий адмінам, створюють запис через
  `AdminNotificationService` — вимога `AGENTS.md`.
