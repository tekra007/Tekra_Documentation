# 20. Політики

> Під ТЗ §4.7.4, §4.1.12–14, §4.6, §4.7.5, §4.5. Рішення D44–D46 — ✅ прийнято
> 2026-09-17. Таблиця — у [03-data-model.md](03-data-model.md), крок 11.

## Політика чи дія

ТЗ перелічує в Admin Panel (§4.7.4) дві різні за природою речі, і їх варто
розвести одразу:

| | Що це | Приклад |
|---|-------|---------|
| **Політика** | правило, яке **діє постійно**, поки його не змінять | «для PROD потрібне погодження» |
| **Дія** | **одноразова** операція адміна | погодити v28, вимкнути робота |

Розкладаємо список ТЗ:

| Пункт Admin Panel з ТЗ | Що це | Де описано |
|------------------------|-------|------------|
| TEST Approval Required ON/OFF | політика | тут |
| дозволені Test Period | політика | тут |
| максимальна тривалість Test Period | політика | тут |
| поведінка після закінчення: ALLOW_TO_FINISH / TERMINATE | політика | тут |
| PROD Approval Required ON/OFF | політика | тут |
| TEST → PROD: глобальна політика + винятки для роботів | політика | тут, D46 |
| Scheduling: priority, concurrency, resource limits, queue policy | політика | блок «Черги й пріоритет» |
| PROD: approval, reject, revoke | **дія** | [17-authorization.md](17-authorization.md) |
| Availability: enable, disable, suspend, resume | **дія** | блок «Черги й пріоритет» |
| Audit: перегляд, фільтри, пошук | **дія** | [19-audit.md](19-audit.md) |

## Що вже є в коді

Перевірено 2026-09-17:

- **поняття «політика» в оркестраторі немає**;
- налаштування організації — звичайні колонки в `organizations`: назва, URL,
  часовий пояс, формат дати, термін дії пароля;
- у Face у налаштуваннях є картка **«Automation defaults»** з перемикачами на
  кшталт «Allow long-running robots (>2h)».

### Знахідка: політика в особистих налаштуваннях адміна

Перемикачі «Automation defaults» зберігаються **в особистих налаштуваннях
кожного адміна** (`/admins/me/preferences`), а не в організації.

Тобто один адмін увімкнув «дозволити довгі роботи», інший бачить вимкнено — і
незрозуміло, що насправді діє. Для особистого вигляду інтерфейсу це нормально,
для правил роботи роботів — ні.

До того ж цих перемикачів **немає в ТЗ**. Що з ними робити — окреме рішення, в
цьому блоці не чіпаємо.

## Де зберігати політики (D44 ✅)

| | Варіант | Плюси | Мінуси |
|---|---------|-------|--------|
| A | колонки в `organizations`, як уже зроблено термін дії пароля | найпростіше | таблиця змішує профіль організації з правилами Studio й розростається |
| B | універсальна таблиця `policies`: тип + параметри в JSON + «активна» | гнучко: будь-які політики, будь-яка область дії | параметри без типів і валідації; щоб дізнатись поточне значення, треба ще й правило пріоритету |
| C | **окрема типізована таблиця `organization_policies`**: один рядок на організацію, кожна політика — своя колонка | зрозуміло, з типами, легко читати й перевіряти | нова політика — нова колонка |

### Рішення — C

Політик у ТЗ небагато й вони відомі наперед. Тому типізовані колонки дають
більше, ніж гнучкість JSON: помилку «тривалість = банан» відсіче сама база.

**Як лягають події аудиту ТЗ (§4.7.5):**

| Подія ТЗ | Коли |
|----------|------|
| `POLICY_CREATED` | рядок політик створюється разом з організацією, зі значеннями за замовчуванням |
| `POLICY_ACTIVATED` / `POLICY_DEACTIVATED` | перемикач увімкнули / вимкнули |
| `POLICY_CHANGED` | змінили значення: тривалість, поведінку після закінчення |

Усе пишеться в `audit_events` за D41–D42: хто, коли, було → стало.

### Значення за замовчуванням для нової організації

ТЗ їх не задає. Прийнято:

| Політика | За замовчуванням | Чому |
|----------|------------------|------|
| TEST Approval Required | **вимкнено** | ТЗ §4.1.12 описує Test Period як потрібний «лише якщо увімкнено» — тобто вимкнено — звичайний стан. Не гальмує перші кроки |
| PROD Approval Required | **увімкнено** | продакшен за замовчуванням захищений — безпечніше помилитись у цей бік |
| Готові тривалості Test Period | 1h, 3h, 1d, 2d, 1 week | рівно список із ТЗ §4.1.12 |
| Довільна тривалість (custom) | дозволено | є в тому ж списку ТЗ |
| Максимальна тривалість | 1 тиждень | найбільше значення зі списку ТЗ |
| Після закінчення періоду | **ALLOW_TO_FINISH** | мʼякший варіант: не обриває робота посеред роботи |

### Хто бачить і змінює

| | Бачить поточні значення | Змінює | Бачить історію змін |
|---|---|---|---|
| Admin | так | так (`POLICY_EDIT`) | так |
| Developer | так, лише читання | ні | ні (D43) |
| Regular User | ні | ні | ні |

Розробнику поточні значення потрібні: він має розуміти, чи попросить Studio
погодження перед PROD і чи треба тестовий період.

## Зміна політики заднім числом не діє (D45 ✅)

### Питання

Адмін змінив політику, а в системі вже щось відбувається: версії в PROD, запити
на погодженні, запущені роботи. Що з ними?

### Рішення

**Політика читається в момент дії і заднім числом не застосовується.**

| Зміна | Що з тим, що вже є |
|-------|--------------------|
| PROD Approval Required: вимкнено → увімкнено | версії, що вже в PROD, лишаються. Наступний Move to PROD — уже з погодженням |
| PROD Approval Required: увімкнено → вимкнено | запити, що вже чекають, **не погоджуються автоматично** — лишаються на рішення адміна |
| TEST Approval Required: вимкнено → увімкнено | нові TEST-запуски без чинного періоду → BLOCKED. Уже запущені — доробляють |
| TEST Approval Required: увімкнено → вимкнено | тестувати можна без періоду; видані періоди просто перестають бути потрібними |
| змінили поведінку після закінчення | діє значення **на момент** закінчення періоду |
| зменшили максимальну тривалість | уже видані періоди **не скорочуються** |

Чому саме так: інакше одне натискання в налаштуваннях мовчки змінює рішення, які
адміни чи розробники вже ухвалили. Наприклад, вимкнули обовʼязкове погодження — і
десяток запитів, які адмін свідомо ще не розглянув, раптом опинились у PROD.

## TEST → PROD у MVP (D46 ✅)

### Що каже ТЗ

§4.6: TEST-робот не повинен напряму взаємодіяти з PROD-роботом. Базова політика
— `DENY ALL`, можливі винятки для конкретних пар роботів з дозволами READ /
CALL / WRITE / TRIGGER. Точна семантика дозволів — відкрите питання ТЗ #8, а
«тільки через Orchestrator API» — #9.

### Знахідка

У MVP **немає жодного способу**, яким один робот може звернутись до іншого:

- у каталозі активностей (D6) немає кроку «викликати іншого робота»;
- Custom components (D33) — це складання кроків в один компонент, а не виклик
  іншого робота.

Отже базова політика `DENY ALL` у MVP виконується **сама собою** — порушити її
нічим.

### Рішення

- глобальна політика — `DENY ALL`, **фіксована**. У налаштуваннях показуємо її
  як текст, без перемикача;
- таблицю винятків і семантику READ / CALL / WRITE / TRIGGER (#8, #9)
  проєктуємо **разом із першим способом викликати іншого робота** — це
  найімовірніше станеться в BPMN (D33), де процес складається з задач різних
  роботів.

Критерій ТЗ №37 («TEST → PROD interaction контролюється policy») при цьому
виконується: взаємодій, які треба контролювати, у MVP просто немає.

## Що свідомо не вирішуємо тут

- **Політики черг** — priority, concurrency, resource limits, queue policy.
  Колонки додамо в ту ж таблицю в блоці «Черги й пріоритет».
- **«Automation defaults»** у Face — що робити з перемикачами, яких немає в ТЗ і
  які зберігаються в особистих налаштуваннях адміна.
- **Умови автоматичного SUSPENDED** (питання ТЗ #10) — теж блок «Черги й
  пріоритет», разом з Availability.
