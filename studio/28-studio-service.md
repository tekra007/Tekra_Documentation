# 28. Studio — окремий сервіс

> Рішення D31 (переглянуто), D67, D68 — ✅ прийнято 2026-10-05. Переглядає D15 і
> уточнює D41, D62. Попереднє обговорення «ділити чи ні» —
> [15-service-split.md](15-service-split.md), лишається як історія.

## Головне

**Бекенд Studio — окремий сервіс** зі своєю БД і своїм репозиторієм
(`Tekra-Studio`, створимо пізніше). Фронт Studio лишається в
`Tekra-Orchester-Face`.

Бекенд Studio говорить **лише з оркестратором** і лише **через брокер**
(RabbitMQ + FastStream). З десктопом він не говорить ніколи (ТЗ §2.3, §4.8, D5) і
в БД оркестратора не лізе.

Так влаштовано і в ТЗ: Studio — окремий компонент, який передає в оркестратор
«Robot / Version / Status / Changes» (§2, §4.7.1).

## Хто з ким говорить (D31 ✅, варіант II)

```
                         Браузер (Face)
            ┌───────────────────┴────────────────────┐
     редагування робота                      усе, що виконується й погоджується:
     робоча копія, версії, компоненти,       запуски, логи наживо, Inspector,
     процеси, перевірка сценарію             машини, погодження, Test Period,
            │                                аудит, політики, Lifecycle
     HTTP   │                                        │ HTTP + WS
            ▼                                        ▼
     Studio-сервіс ◄═══ RabbitMQ (FastStream) ═══► Оркестратор ◄── WS ── Десктоп
            │                                        │              (/users/ws)
       БД Studio                               БД оркестратора
```

- Inspector і логи наживо йдуть браузер → оркестратор → десктоп, як і зараз —
  без зайвої ланки. Це знімає головне заперечення з D31.
- Ззовні — одна адреса: проксі розводить `/studio-api/…` у Studio, решту — в
  оркестратор.

## Що де живе

ТЗ §8: «Створити Robot'а — Developer; Orchestrator **зберігає / контролює**»,
«Створити Version — Developer; Orchestrator **зберігає**». Тобто **створює —
розробник у Studio, зберігає й контролює — оркестратор.**

| Studio (своя БД) — **створює** | Оркестратор (своя БД) — **зберігає й контролює** |
|---|---|
| нові роботи: UUID і номер `RBT-184` (D68) | реєстр роботів — копія з подій Studio |
| назва, опис, власник робота — змінюються тут | ті самі поля — копія, + аудит змін |
| робоча копія робота й `working_copy_base_number` (D34, D63) | **стани робота**: Lifecycle, Authorization, Availability, Health, Active Production Version |
| **версії роботів** — створюються тут, номер `184.13` (D68) | **версії роботів** — повна копія з події; з неї виконують |
| компоненти та їхні версії (D58, D64) | — версії робота вже містять їхній вміст |
| BPMN-процеси (D57) | — |
| каталог активностей, перевірка сценарію (D2, D14) | машини, облікові дані, розклади, запуски, погодження, Test Period, політики, аудит |

Чому копія версії в оркестраторі безпечна: версія — **повний незмінний знімок**
(D64). Studio надсилає її один раз, повністю, і синхронізувати потім нічого.

**Хто що змінює:**

| Дія | Де | Як дізнається інший |
|-----|----|---------------------|
| створити робота, перейменувати, змінити опис чи власника | Studio | подія → оркестратор оновлює реєстр і пише аудит |
| «Зберегти» — нова версія | Studio | подія → оркестратор реєструє версію й пише аудит |
| Перевести в TEST, запустити, Move to PROD, погодити, rollback, вимкнути, архівувати, видалити | оркестратор (браузер іде туди напряму) | архівування, відновлення, видалення → подія в Studio, вона блокує або розблоковує робочу копію |

## Studio не чекає оркестратор (D68 ✅, варіант B)

Студія працює далі, навіть коли оркестратор недоступний:

- **номер робота** видає Studio — лічильник організації в БД Studio. Номери не
  перевикористовуються (D62);
- **номер версії** видає Studio — «найбільший + 1» у межах робота. Конфліктів
  немає: версії створює **лише** Studio;
- «Зберегти» — Studio записує версію в себе й ставить подію у outbox. Користувач
  одразу бачить `184.13`. Подія доставиться, щойно оркестратор підніметься.

### Зберегти й запустити

Запуск — у оркестраторі, тож він має знати версію. Тому:

```
 «Запустити» з незбереженими змінами
   1. браузер → Studio: зберегти          → Studio: «184.13, ще не зареєстрована»
   2. оркестратор отримав подію, зареєстрував версію → подія «registered» → Studio
   3. Studio позначає 184.13 зареєстрованою → браузер бачить це
   4. браузер → оркестратор: запустити 184.13
```

Зазвичай кроки 1–3 тривають мілісекунди — для розробника це одне натискання. Поки
версія не зареєстрована, кнопка показує «передаю версію в оркестратор…». Якщо
оркестратор лежить — запустити й так неможливо, а збережена версія не
загубиться.

### Перевірки, яким потрібен оркестратор

Частина перевірок сценарію (D14) питає оркестратор: чи є машина, що вміє потрібні
провайдери; чи не видалено облікові дані. Це **запит-відповідь** через брокер.

Якщо оркестратор не відповів за тайм-аут — збереження **дозволене**, ці перевірки
позначаються «не перевірено». Перед запуском їх однаково зробить оркестратор (17
перевірок, D48).

## Брокер (D67 ✅)

**RabbitMQ + FastStream.** FastStream — Python-бібліотека поверх брокера, не
сам брокер.

| | MVP | Пізніше |
|---|---|---|
| RabbitMQ | один вузол, черги на диску (durable) | кластер із 3 вузлів, **quorum queues** — повідомлення підтверджується, коли його записала на диск більшість вузлів. Код не змінюється |

З RabbitMQ 4.0 дзеркалювання класичних черг прибрано — для відмовостійкості лише
quorum queues.

**Чому не інші:** Kafka — завеликий для нашого обсягу й незручний для
запит-відповідь; Redis Streams — слабкий у надійності при перемиканні вузлів;
NATS JetStream — гідна альтернатива, але RabbitMQ поширеніший і має вбудований
запит-відповідь (direct reply-to), який FastStream підтримує через
`broker.request()`.

### Правила надійності

Брокер гарантує, що **прийняте** повідомлення не загубиться. Решту закривають
сервіси:

| Правило | Що закриває |
|---------|-------------|
| **Outbox**: подія пишеться в таблицю `outbox` тієї ж БД **у тій самій транзакції**, що й зміна; окремий процес надсилає її в брокер і позначає надісланою лише після підтвердження брокера (publisher confirms) | «записали в БД, а надіслати не встигли» |
| **Inbox / ідемпотентність**: кожне повідомлення має `message_id`; отримувач записує його в `inbox` у тій самій транзакції, що й обробку, і повтор пропускає | брокер доставляє «хоча б раз» — можливі дублікати |
| **Підтвердження обробки вручну** (manual ack) — лише після коміту | впав посеред обробки — повідомлення прийде знову |
| **Черга для «отруйних» повідомлень** (dead letter): після N невдалих спроб повідомлення відкладається, адмін бачить його | одне битe повідомлення не блокує решту |
| **Порядок**: у MVP одна черга на отримувача й один обробник | «версію створено» не прийде раніше за «робота створено» |

Outbox і inbox — в **обох** сервісах: події ходять в обидва боки.

### Конверт повідомлення

```json
{
  "message_id": "uuid",
  "type": "studio.robot_version.created",
  "schema_version": 1,
  "occurred_at": "2026-10-05T12:00:00Z",
  "organization_id": "uuid",
  "actor_user_id": "uuid",
  "correlation_id": "uuid",
  "payload": { }
}
```

`occurred_at` і `actor_user_id` — для аудиту: оркестратор пише подію з часом і
автором дії в Studio, а не з часом доставки.

### Перелік повідомлень (перша версія)

**Події Studio → оркестратор** (exchange `studio.events`):

| `type` | Що | Оркестратор |
|--------|----|-------------|
| `studio.robot.created` | UUID, номер, назва, опис, власник, автор | додає в реєстр (Lifecycle = DRAFT), аудит |
| `studio.robot.updated` | що змінилось: назва / опис / власник | оновлює, аудит із «було → стало» |
| `studio.robot_version.created` | `robot_id`, `number`, повний `definition`, `definition_hash`, опис змін, `min_assistant_version`, автор | реєструє версію (Release State за D39), аудит, відповідає `registered` |
| `studio.component_version.created`, `studio.component.archived`, `studio.process_version.created` | | лише аудит |

**Події оркестратор → Studio** (exchange `orchestrator.events`):

| `type` | Studio |
|--------|--------|
| `orchestrator.robot_version.registered` | позначає версію зареєстрованою — можна запускати |
| `orchestrator.robot.archived` / `restored` | блокує / розблоковує робочу копію |
| `orchestrator.robot.deleted` | видаляє робочу копію й версії в себе |

**Запит-відповідь Studio → оркестратор** (direct reply-to, з тайм-аутом):

| Запит | Навіщо |
|-------|--------|
| `orchestrator.machines.capabilities` | перевірка: чи є машина з потрібними провайдерами й версією агента (D14) |
| `orchestrator.credentials.exist` | перевірка: чи не видалено облікові дані, на які посилається сценарій (D20) |

Розмір повідомлення в RabbitMQ обмежений налаштуванням — при реалізації звірити
з найбільшим `definition`. Знімки елементів (D7a) у версію за потреби кладемо
посиланням, а не байтами.

## Що ще змінилось у попередніх рішеннях

Звірка D1–D68 з окремим сервісом, 2026-10-05.

| Що | Як тепер | Рішення |
|----|----------|---------|
| **Каталог активностей** | живе в `Tekra-Studio`: форми кроків, перевірка сценарію, розрахунок `min_assistant_version`. Оркестратору не потрібен. Контрактний тест «реалізовано на десктопі == є в каталозі» — теж у `Tekra-Studio` | D2 (змінено) |
| **Inspector** | браузер → оркестратор → десктоп, як і було. Оркестратор лише пересилає `INSPECT_RESULT` (селектор, знімок, скріншот) у браузер і **нічого не зберігає**; браузер кладе елемент у бібліотеку робочої копії через API Studio. Брокер тут не бере участі | D5, D7a, D21 |
| **Здоровʼя процесу** | Studio його не рахує й Health роботів у себе не копіює: екран процесу бере склад процесу зі Studio, а Health його роботів — з оркестратора (браузер ходить в обидва) | D57 |
| **Цілісність версії** | при реєстрації оркестратор **сам перераховує `definition_hash`**. Не збігся — версія не реєструється, повідомлення йде в чергу «отруйних», адміни отримують сповіщення. Сценарій наново не перевіряє — це робота Studio; готовність перед запуском дивляться 17 перевірок | ТЗ §4.1.5 «контроль цілісності» |

Не зачеплено: запуски, черги, погодження, Test Period, аудит (крім уточнення
нижче), політики, машини, облікові дані, розклади — усе лишається в оркестраторі.

## Аудит (D41 — уточнення)

D41: аудит пишеться в тій самій транзакції, що й зміна стану. Для дій, що
починаються в Studio, це виконується так:

- Studio пише зміну й подію в outbox **однією транзакцією** — подія не загубиться;
- оркестратор застосовує подію (оновлює реєстр, реєструє версію) і пише аудит
  **однією транзакцією** — аудит не розійдеться зі станом у оркестраторі.

Журнал аудиту один — в оркестраторі (ТЗ §4.7.5). Studio свого журналу не веде.

## Вхід і доступ

- Токени, як і зараз, видає оркестратор. Studio перевіряє підпис **сама**, без
  звернення до оркестратора.
- Зараз токени підписуються `SECRET_KEY` (`src/utils/jwt_token.py`). Якщо це
  симетричний ключ, Studio довелося б мати той самий секрет — і вона змогла б
  **підробляти** токени. Тому: **пара ключів** — оркестратор підписує приватним,
  Studio перевіряє публічним (наприклад, RS256 або EdDSA).
- Права на дії в Studio (`ROBOT_CREATE`, `ROBOT_EDIT`, `VERSION_CREATE` — D56)
  перевіряє Studio за роллю з токена. Права на дії в оркестраторі — оркестратор.
- Доступ до брокера — окремі облікові записи RabbitMQ для кожного сервісу, кожен
  лише до своїх exchange і черг.

## Розгортання

```
 docker-compose
   api (оркестратор)   postgres   redis   rabbitmq   studio
```

- БД Studio — окрема база (можна на тому самому сервері Postgres);
- Redis лишається для обмеження частоти запитів;
- RabbitMQ — вебпанель лише у внутрішній мережі.
