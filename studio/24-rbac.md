# 24. Visibility і Permissions

> Під ТЗ §4.4, §4.5, §8, §4.1.2. Закриває відкрите питання ТЗ **#14**. Переглядає
> D25. Рішення D56 — ✅ прийнято 2026-09-17 після звірки з ТЗ.

## Головне

ТЗ розводить два поняття (§4.4):

- **Visibility** — що людина **бачить**;
- **Permission** — що людина **може зробити**.

Тому нижче дві окремі матриці.

Ролі — наявні `USER` / `DEVELOPER` / `ADMIN` (D23). У MVP матриця **фіксована в
коді**, налаштовуваних ролей немає. Перевіряється **на бекенді** — ховати кнопки
недостатньо (D25).

## Розділення обовʼязків

Матриця відповідальності ТЗ (§8) розводить ролі чітко:

| | Developer | Admin |
|---|---|---|
| створює й редагує робота, створює версію | так | — |
| тестує | ініціює | лише тестовий період, якщо потрібен |
| Move to PROD | ініціює | — |
| погоджує / відхиляє PROD | — | так |
| production execution | запитує за RBAC | задає політику |

Звідси головне правило:

> **Хто подає в PROD — не погоджує. Хто погоджує — не подає.**

Так виконується і §4.1.2: «хто створив версію», «хто виконав release» і «хто
виконав approval» — різні люди. Якби адмін міг сам створити версію, сам подати й
сам погодити, погодження втратило б сенс.

## Visibility — що бачить

Верхня частина — таблиця ТЗ §4.4 з уточненням, що означає «за RBAC». Нижня —
сутності, яких у ТЗ немає.

| Обʼєкт | Regular User | Developer | Admin |
|--------|--------------|-----------|-------|
| DRAFT Robot | ні | так | так |
| TEST Robot | ні | так | так |
| PROD Robot | роботи, до яких має доступ (`robot_access`) | так | так |
| ARCHIVED Robot | ні | так | так |
| TEST Version | ні | так | так |
| PROD Version | версії доступних роботів | так | так |
| TEST Execution | ні | так | так |
| PROD Execution | **дозволені** — запуски доступних роботів | **дозволені** — у MVP розробнику доступні всі роботи організації (D25) | так |
| Approval | лише статус | лише статус (D43) | так |
| Test Period | ні | власні й запитані | так |
| Audit | ні | обмежено (D43) | так |
| **Машини** | ні | усі в організації — щоб обрати, де запускати | так |
| **Облікові дані** | ні | назва й логін, **без пароля** (D20) | назва й логін, без пароля |
| **Політики** | ні | поточні значення, лише читання (D44) | так |
| **Процеси (BPMN)** | ні | так | так |
| **Компоненти** | ні | так | так |

Пароль облікових даних не бачить **ніхто**, зокрема адмін (D20).

**Про аудит.** Два місця ТЗ тут трохи розходяться: у §8 у розробника біля Audit
прочерк, а в §4.4 — «обмежено». §8 — про відповідальність за ведення аудиту, §4.4
— саме про видимість, тож ідемо за §4.4.

### Чого в ТЗ немає і як покрито

| Дія | Хто | Чому |
|-----|-----|------|
| rollback | розробник (`ROBOT_MOVE_TO_PROD`) **або** адмін (`PROD_APPROVE`) | перемикає лише між уже погодженими версіями — нічого нового не подається й не погоджується, тож розділення обовʼязків не порушено (D53) |
| відновлення з архіву | `ROBOT_ARCHIVE` | повертає лише в TEST, у PROD — знову через подачу й погодження (D55) |
| процеси й компоненти | `ROBOT_CREATE` / `ROBOT_EDIT` — розробник | окремих дозволів у ТЗ немає; це та сама робота розробника (D57, D58) |
| машини, облікові дані | адмін | налаштування організації, а не робота над роботом |
| розклади | розробник — через версію робота | за ТЗ §4.1.4 тригери — частина версії (D58), тож змінюються як будь-яка зміна робота |
