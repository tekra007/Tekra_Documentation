# 33. Фаза 1 — тонка нитка: задачі

> Розбивка фази 1 з [10-roadmap.md](10-roadmap.md) на задачі. Складено
> 2026-11-06 на основі документів і поточного коду (перевірено того ж дня).
> Правила роботи — [10-roadmap.md, «Як реалізуємо»](10-roadmap.md#як-реалізуємо).
>
> **Мета фази 1:** робот з **одного кроку** проходить увесь шлях через усі частини —
> Studio-front → Studio-back → RabbitMQ → оркестратор → десктоп → назад у
> Studio-front. Некрасиво, без редактора й Inspector — але всі інтеграційні
> сюрпризи (брокер, outbox, токени, WS, UIA у зібраному `.exe`) знімаються, поки
> коду мало.

```
Studio-front ──HTTP──► Studio-back: створити робота, сценарій — сирий JSON з одним кроком desktop-uia/Click
                  │ «Зберегти» → версія 1 + подія в outbox
                  ▼
               RabbitMQ
                  ▼
           Оркестратор: перерахував хеш, зареєстрував версію, аудит → подія «registered»
Studio-front ──HTTP──► Оркестратор: (DRAFT → TEST) і запуск TEST на своїй машині
                  │ EXECUTION_ASSIGN
                  ▼
           Десктоп: справді клікнув → лог і результат
                  ▼
Studio-front ◄──WS─── Оркестратор: «COMPLETED» і логи
```

## Як читати задачу

Як у [фазі 0](30-phase-0.md): **що**, **де**, **від чого залежить**, **схема**
(міграції пише агент, комітить людина) і **готово, коли** — перевіряні критерії.

## Порядок

```
J1 схема → J2 контракти → J3 формат
   ├── K1 роботи (Studio) ─► K2 версії ─────────────┐
   ├── L1 реєстр ─► L2 реєстрація версії ─┐         │
   └── L3 Assistant і машина ─► N1         │         │
                                           ▼         ▼
                         L4 запуск TEST ◄──┘    K3 Studio-front
                         N2 виконавець ─► N3 збірка
                         L5 події в браузер
                                           ▼
                                   O1 · O2 наскрізь
```

Studio (K) і оркестратор (L) після J2 йдуть паралельно: вони говорять лише
контрактами.

## Відкриті питання — вирішити до коду

1. **Стара zip-модель.** D14: старе не тягнемо, співіснування немає. Таблиця
   `robots` в оркестраторі потрібна новому реєстру. Пропоную **прибрати zip-модель у
   фазі 1 повністю**: в оркестраторі — стару `robots`, `robot_kpi`, старі
   ендпоінти запуску й WS-команди `add_robot` / `load_robots` / `robot_kpi`; у
   десктопі — розпакування архівів, `ProcessManager` / `RobotLayout`, старий
   розклад. Головне вікно десктопа показує стан підключення й запуски, які він
   виконує. Альтернатива — перейменувати стару таблицю й прибрати у фазі 2, але
   це рік гілок «старий / новий» у коді.
2. **На якій машині розробник може запустити TEST.** У документах не визначено.
   Пропоную: лише на машині, де в Assistant **зараз увійшов він сам**; адмін TEST
   не запускає (D56). Для цього `assistants.signed_in_account_id` оновлюється при
   вході й виході.
3. **Канал подій для Studio-front.** Пропоную `/me/ws` (уже відкритий будь-якому
   учаснику) з підпискою на `execution_id`; сповіщення адмінам ідуть, як і зараз,
   лише адмінам. Відомо: як і дзвіночок (H2), цей канал у межах одного процесу API —
   для однієї копії API достатньо.
4. **«Запустити» в Studio-front.** Пропоную одну кнопку: зберегти (D34) → дочекатися
   `registered` → якщо робот у DRAFT, перевести в TEST (21-queues: інакше перший
   запуск упирається в BLOCKED) → запуск.
5. **Тайм-аут черги.** Пропоную задачу в процесі планувальника (H1) раз на 30 с:
   QUEUED довше 5 хв → BLOCKED з причиною; плюс відправка черги щойно Assistant
   підключився.
