# Tekra Studio — коротко для команди

> Вижимка на 10 хвилин. Усе детально — у [README](README.md) розділу; при
> розбіжності правду кажуть [ТЗ](spec/tz-lifecycle.md) і
> [модель розгортання](spec/deployment-model.md). Станом на 2026-10-20.

## Що будуємо

**RPA-платформу.** Людина **у браузері** збирає робота з кроків: «відкрий 1С»,
«натисни кнопку», «прочитай рядки з Excel», «для кожного рядка — внеси
документ». А робот **на компʼютері** виконує ці кроки в справжніх програмах
замість людини — вдень на очах у користувача або вночі за розкладом.

Робота не пишуть кодом: сценарій — це JSON зі списку кроків, який будується в
редакторі. Елементи екрана (кнопки, поля) «ловляться» мишкою прямо в програмі.

Кожен робот проходить шлях **TEST → PROD**: розробник тестує скільки треба, а в
бойову роботу робот потрапляє лише після погодження адміном. Усе, що
змінює стан, пишеться в аудит.

Продається у двох режимах (модель розгортання):

- **Free / Trial** — одне спільне середовище на багато організацій-клієнтів;
- **Paid / Enterprise** — окрема копія платформи на кожного клієнта: у нашій
  хмарі, у хмарі клієнта або на його серверах.

Код один для обох режимів — різниться лише те, як його розгорнуто.

## З чого складається

```
 Studio-front (розробник)                    Face (адмін, Regular User)
   │              │                                     │
   │ редагування  │ тестові запуски, логи,              │ погодження, політики,
   │              │ Inspector, Move to PROD             │ машини, аудит
   ▼              └─────────────┐     ┌─────────────────┘
 Studio-back ◄══ RabbitMQ ══► Оркестратор ◄──── WS ────► Assistant
   │                                  │                  (десктоп на ПК клієнта)
 своя БД                           своя БД                     │
                                                         клацає в 1С, BAS,
           Keycloak — вхід для всіх                      Excel, браузері
```

| Частина | Що робить | Репозиторій |
|---------|-----------|-------------|
| **Studio-front** | застосунок **розробника**: редактор роботів, версії, тестові запуски й логи наживо, Inspector, компоненти, процеси, Move to PROD. Ходить у Studio-back і напряму в оркестратор | `Tekra-Studio-front` (Angular) — **новий** |
| **Studio-back** | **створює**: роботів, їхні версії, компоненти, BPMN-процеси; перевіряє сценарій перед збереженням; видає номери `RBT-184`, `184.2` | `Tekra-Studio-back` — **новий** |
| **Face** | **адмін-панель** оркестратора: погодження, політики, аудит, машини, користувачі, ліцензії; плюс запуск PROD-роботів для Regular User | `Tekra-Orchester-Face` (Angular) |
| **Оркестратор** | **зберігає й контролює**: стани роботів, копії версій, запуски й черги, погодження, тестові періоди, політики, аудит, машини, облікові дані, розклади | `Tekra-Orchester` (FastAPI) |
| **Assistant** | десктоп-агент на ПК клієнта: виконує запуски, ловить елементи екрана, шле логи. Нічого сам не вирішує | `Tekra-Desktop` (PyQt6) |
| **Keycloak** | вхід і акаунти: один акаунт людини, у різних організаціях — різні ролі | готовий сервер |
| **RabbitMQ** | «пошта» між Studio й оркестратором: доставить, навіть якщо отримувач на хвилину впав | готовий сервер |

Studio-back й оркестратор — **окремі сервіси** з окремими базами. Наприклад, Studio
може зберегти нову версію, навіть коли оркестратор недоступний: подія доїде,
щойно він підніметься.

## Головні поняття

| Поняття | Що це | Як виглядає |
|---------|-------|-------------|
| **Організація** | клієнт (тенант). Усе — роботи, машини, люди, запуски — належить організації | номери скрізь свої в кожній організації |
| **Робот** | одна автоматизація | `RBT-184` |
| **Версія** | повний **незмінний** знімок робота: усі кроки, елементи, параметри, розклади. Зберігаємо цілком, а не різницю з попередньою | `184.2` — робот 184, версія 2 |
| **Компонент** | готовий шматок сценарію, який вставляють у різних роботів як один крок («Увійти в BAS») | `CMP-7`, версія `7.3` |
| **Процес** (BPMN) | схема бізнес-процесу з **Business Tasks** — задач, які виконує людина, AI, зовнішня система або робот | `PRC-12` |
| **Запуск** (Execution) | одне виконання конкретної версії в контексті TEST або PROD | QUEUED → RUNNING → COMPLETED / FAILED; або BLOCKED з причиною |
| **Lifecycle** | етап робота | DRAFT → TEST → PROD → ARCHIVED |
| **Погодження** | рішення адміна пустити версію в PROD (або дати тестовий період) | PENDING → APPROVED / REJECTED |
| **Assistant і машина** | Assistant — встановлена програма-агент; машина — компʼютер, де вона стоїть. Окремі сутності, один Assistant на машину | `ASSISTANT-104` на `MACHINE-27` |

## Як живе робот

```
 1. Розробник створює робота в Studio                       → RBT-184, DRAFT
 2. Збирає кроки, тисне «Зберегти»                          → версія 184.1
 3. Переводить у TEST і запускає на своїй машині стільки разів, скільки треба;
    правки → «Зберегти» → 184.2, 184.3 …
 4. Обирає версію й тисне «Move to PROD»                    → чекає погодження
 5. Адмін погоджує                                          → 184.3 активна в PROD
 6. Робот працює: вручну за кнопкою або за розкладом уночі
 7. Тим часом розробник робить 184.4 — PROD це не зачіпає, доки 184.4 не погодять
 8. Нова версія зламалась? Rollback на 184.3 — один клік, без нового погодження
 9. Робот більше не потрібен                                → ARCHIVED
```

## Десять правил, які не порушуємо

| # | Правило | Чому |
|---|---------|------|
| 1 | **Версія незмінна.** Змінили робота — нова версія | погоджували саме цю реалізацію; тиха зміна обійшла б погодження |
| 2 | **Запуск — завжди конкретної версії** (`184.2`) | завжди видно, що саме виконувалось і чому впало |
| 3 | **У PROD — лише через погодження.** Хто подає — не погоджує, хто погоджує — не подає | інакше погодження нічого не варте |
| 4 | **Studio створює, оркестратор зберігає й контролює** | одна правда про стан робота — в оркестраторі |
| 5 | **Між Studio й оркестратором — лише RabbitMQ**, з outbox / inbox | подія не загубиться, якщо сервіс упав, і не обробиться двічі |
| 6 | **Studio ніколи не говорить з десктопом** — усе через оркестратор | контроль, черги й перевірки — в одному місці |
| 7 | **Аудит — у тій самій транзакції**, що й зміна | не записався аудит — не відбулась зміна; історію не обійти |
| 8 | **Організації не бачать одна одну** — фільтр у кожному запиті + Row-Level Security у Postgres | у Free на одному сервері багато клієнтів; витік між ними — катастрофа |
| 9 | **Паролі ніде не показуються й не логуються** | робот логіниться в бухгалтерію клієнта; пароль бачить лише сам робот у момент входу |
| 10 | **Перед запуском — 17 перевірок оркестратора** | робот у правильному стані, погоджений, машина на звʼязку, облікові дані вільні… Не пройшло — BLOCKED з причиною, а не падіння посеред сценарію |

## Порядок робіт

Спершу — **тонка нитка**: найпростіший робот проходить через усі частини.
Далі — нарощування.

| Фаза | Що | Результат |
|------|-----|-----------|
| **0. Фундамент** | `Tekra-Studio-back`, `Tekra-Studio-front`, RabbitMQ, Keycloak, аудит, безпека | частини існують і можуть говорити одна з одною |
| **1. Тонка нитка** | робот з одного кроку «клікнути»: Studio-front → Studio-back → RabbitMQ → оркестратор → десктоп | справжній клік на справжній машині, видно в Studio-front. Усі інтеграційні сюрпризи — позаду |
| **2. Executor** | змінні, умови, цикли, обробка помилок; Windows-програми | робот виконує справжній сценарій |
| **3. Inspector** | захоплення кнопок і полів мишкою | робота можна зібрати без ручного JSON |
| **4. Редактор Studio** | форми кроків, бібліотека елементів, перевірка сценарію, облікові дані | розробник збирає робота в браузері |
| **5. Виконання повністю** | черги, 17 перевірок, блокування облікових даних, логи наживо | надійний TEST |
| **6. Шлях у PROD** | погодження, тестові періоди, політики, rollback, архів | усе з ТЗ |
| **7. Розклад** | запуск уночі | головна цінність для бізнесу |
| **8. Розширення** | компоненти, BPMN-процеси, точки зупинки | |
| **9–10** | Excel, браузер | |

Після MVP: Marketplace, тарифи й ліміти Free, ліцензія на deployment, перехід
Free → Paid.

### Фаза 0 — що саме

| Що | Навіщо |
|----|--------|
| каркас `Tekra-Studio-back` — той самий стек, що в оркестратора (FastAPI, SQLAlchemy async, Alembic) | новий сервіс |
| каркас `Tekra-Studio-front` — Angular у стилі Face, свій код | застосунок розробника |
| RabbitMQ + FastStream, outbox / inbox в обох сервісах; схеми повідомлень — у `Tekra-Orchester` | звʼязок Studio ↔ оркестратор |
| Keycloak: акаунт + членство в організації з роллю ADMIN / DEVELOPER / USER | один вхід для Studio-front, Face і десктопа |
| аудит — окрема таблиця, лише дописування | вбудувати з першого дня дешевше, ніж дописувати потім |
| ізоляція організацій: фільтр + Row-Level Security | зараз фільтр ставиться вручну, і в одному місці його вже забули |
| шифрування секретів ключем організації | облікові дані роботів і секрети адмінів не лежать відкрито |
| закрити CORS і Redis | зараз CORS відкритий для всіх, Redis без пароля |
| планувальник — окремим процесом | інакше дві копії оркестратора запускатимуть задачі двічі |
| адреса API для обох фронтів — під час запуску, а не при збірці | одна збірка на всі середовища; фронти ставляться і на Vercel, і в клієнта |
| підключення Assistant за токеном від адміна + версія протоколу | користувач не вводить адресу сервера руками; deployment оновлюються окремо від ПК |
