## Проблема: шість станів

У робота шість незалежних вимірів (ТЗ §4.3), і зводити їх в один статус ТЗ
забороняє. Але список, де в кожному рядку шість кольорових бейджів, читати
неможливо.

## Принцип показу (D59 🟡)

> **У списках — лише те, що вимагає уваги. У картці — усе й окремо.**

### У списку роботів

| Колонка | Що показує |
|---------|------------|
| Назва, `RBT-000184` | |
| **Lifecycle** | завжди: DRAFT / TEST / PROD / ARCHIVED |
| **Активна версія** | лише для PROD: `v27` |
| **Потребує уваги** | бейджі **лише ненормальних** станів |

Що вважається ненормальним:

| Вимір | Бейдж зʼявляється, коли |
|-------|--------------------------|
| Authorization | PENDING_APPROVAL, REJECTED, REVOKED, EXPIRED |
| Availability | DISABLED, SUSPENDED |
| Health | WARNING, ERROR, OFFLINE |
| Останній запуск | FAILED, BLOCKED |

Робот у PROD, погоджений, увімкнений і здоровий — у колонці «Потребує уваги»
порожньо. Порожньо = усе добре.

Виміри при цьому **не зливаються** — кожен бейдж окремий і називає свій вимір.
Вимога ТЗ стосується моделі даних, і вона дотримана.

### У картці робота

Шапка — усі виміри поруч, кожен зі своєю назвою:

```
 RBT-000184 · Обробка рахунків
 Lifecycle: PROD   Активна версія: v27   Authorization: APPROVED
 Availability: ENABLED   Health: WARNING   Останній запуск: COMPLETED
```

Вкладки: **Версії** · **Запуски** · **Погодження** · **Тестові періоди** ·
**Розклади** · **Доступ** · **Аудит**.

### Дії в картці робота

| Дія | Хто | Що просить |
|-----|-----|------------|
| Запустити | за правами | якщо робот у DRAFT — одразу переводить у TEST (D48) |
| Move to PROD | Developer, Admin | версію й коментар |
| Rollback | Developer, Admin | попередню PROD-версію й причину (D53) |
| Вимкнути / Увімкнути | Developer, Admin | причину — за бажанням |
| Призупинити / Відновити | Admin | причину — обовʼязково (D50) |
| Запросити тестовий період | Developer | тривалість із дозволених (D44) |
| Архівувати / Відновити з архіву | Developer, Admin | |
| Видалити | Admin | лише заархівованого (D55) |

### У списку версій

`v28` · **Release State** · **Authorization** · хто створив · хто виконав
release · опис змін · позначка «активна».

### У списку запусків

Статус · **TEST / PROD** · версія · машина · хто запустив · тривалість.
Для BLOCKED — причина. Для RUNNING без звʼязку — позначка «немає звʼязку з
агентом» (D51).

## Нові екрани порівняно з 12-screens

| Екран | Хто | Звідки |
|-------|-----|--------|
| **Погодження** — наявна сторінка Approvals, розширена | Admin | D38: PROD і тестові періоди, погодити / відхилити з причиною |
| **Тестові періоди** | Developer — свої запити; Admin — усі | D37 |
| **Аудит** | Admin; Developer — обмежено | D41–D43: фільтри за роботом, дією, людиною, датою; рядки однієї дії згруповані |
| **Політики** — розділ у налаштуваннях | Admin змінює, Developer бачить | D44 |
| **Процеси** — список, редактор BPMN, моніторинг | Developer, Admin | D57, D60 |
| **Компоненти** — бібліотека | Developer, Admin | D58 |

## Дашборд

`RobotStatusKey = 'RUNNING' | 'PAUSED' | 'ERROR'` суперечить ТЗ: RUNNING буває
в запуску, а не в робота. Пропозиція:

- замість «статусу роботів» — **розподіл Health**: HEALTHY / WARNING / ERROR /
  OFFLINE;
- окремо — **кількість запусків зараз**: RUNNING / QUEUED;
- окремо — **що чекає рішення**: погодження PROD, запити на тестові періоди.

## Навігація: повертаємо «Процеси» (D60 🟡)

Переглядає D29.

| Пункт | Було після D29 | Стає |
|-------|----------------|------|
| **Роботи / Robots** | ✅ | лишається |
| **Процеси / Processes** | прибрано | **повертається** як BPMN-процеси (D57) |
| **Компоненти / Components** | — | новий |

Терміни ТЗ в інтерфейсі:

| У даних і API | В інтерфейсі |
|---------------|--------------|
| Execution | Запуск / Execution |
| Assistant | Assistant — назва десктоп-застосунку |
| Host (`machines`) | Машина / Machine |
| Lifecycle, Authorization, Availability, Health, Release State | як у ТЗ, з перекладом-підказкою |

Принцип D29 лишається: назви беруться з моделі даних, а тепер — із ТЗ, яке стоїть
над моделлю. Помилкою D29 було лише злиття «процесу» з «роботом».

### Борг у коді Face

- повернути пункт навігації «Processes» (BPMN), зберігши «Robots»;
- заглушка сторінки роботів: після D29 там стоїть «список роботів» — правильно;
  для процесів потрібна окрема сторінка;
- дашборд: `RobotStatusKey` → розподіл Health (див. вище).

Код не чіпаємо — фіксуємо.
