# 37. Фаза 5 — виконання повністю: задачі

> Розбивка фази 5 з [10-roadmap.md](10-roadmap.md). Складено 2026-11-08 після фази 4
> ([36](36-phase-4.md)). Рішення ухвалено того ж дня (людина доручила агенту
> вирішувати самому). Підстави — D22, D26, D27, D47–D49, D51, D69, D73, D76,
> [21-queues.md](21-queues.md), [22-availability.md](22-availability.md).
>
> **Мета фази 5:** цикл TEST замкнений: робот приймає **вхідні параметри**, запуск
> можна **скасувати**, облікові дані «лише одна сесія» **не беруть два запуски
> одночасно**, а той, хто чекає, бачить **на що** чекає й чи є **зв'язок** з
> агентом. Адмін задає, які середовища дозволені кожному Assistant.

## Що з roadmap уже зроблено раніше

Фаза 1 (L4, L5) і фаза 4 закрили більшу частину рядка «Виконання повністю»:

| Що | Де зроблено |
|----|-------------|
| черга на машину, PROD першим, один запуск на машину (D47, D49) | L4 — `dispatch_machine`, рядок машини `FOR UPDATE` |
| перевірки двічі — при запиті й перед відправкою (D48) | L4 |
| тайм-аут черги, «не підтвердив за 60 с», «мовчить 30 хв» → FAILED (D48, D51) | L4, планувальник (`sweep`) |
| дозволені середовища Assistant у перевірці №12 (D76) | L4 |
| логи пачками, `ERROR` одразу; живий перегляд за підпискою (D26, D27) | N2, L5 |
| облікові дані існують перед відправкою (№12) | фаза 4, E5 |

## Рішення

| # | Питання | Рішення | Чому |
|---|---------|---------|------|
| 1 | Де оголошуються параметри (D22) | у `definition.parameters`: `[{name, title, type, required, default}]`, `type` — `text` / `number` / `boolean`; `name` — ім'я змінної, унікальне. Поле в спільному контракті `RobotDefinition` (`contracts`, копія в десктопі) | параметри — частина версії, як і кроки; незмінні разом з нею |
| 2 | Як параметр потрапляє в кроки | на старті запуску кожен параметр — змінна (`{{file}}`). Studio-back вважає їх оголошеними з першого кроку; невикористаний параметр — попередження | шаблони вже є (D6b), нового синтаксису не треба |
| 3 | Перевірка значень | оркестратор при `POST /executions { input }`: невідоме ім'я, відсутнє обов'язкове (без `default`), не той тип — **400** з поясненням і слід в аудиті (запуску немає, як і для інших відмов запиту). Порожні — `default`. Зберігається вже повний `input` (`executions.input`) | значення вводить людина — це помилка запиту, не стан, що виправиться сам |
| 4 | Паролі в параметрах | ні: параметри — відкритий текст; секрети — лише облікові дані (D20) | у параметрів немає шифрування й маскування |
| 5 | Блокування облікових даних (D69) | **не окрема таблиця `credential_locks`** (як у 21-queues), а похідне від запусків: запис зайнятий, поки є відправлений / RUNNING / PAUSED запуск, чия версія його використовує. «Разом або нічого» — у транзакції відправки: рядок машини, потім рядки облікових даних `FOR UPDATE` за зростанням id, перевірка, `mark_dispatched` | звільнення неможливо забути: кінець запуску будь-яким шляхом (FINISHED, втрата зв'язку, скасування) звільняє сам. Порядок блокувань однаковий скрізь — без взаємних блокувань |
| 6 | «Хто чекає найдовше» (D73) | запис отримує той, хто попереду в спільній черзі цього запису: PROD перед TEST, далі за `requested_at` — серед **готових** (перший у черзі своєї машини, машина вільна, Assistant на зв'язку). Хто позаду — чекає з причиною «чекає своєї черги на …»; тому, хто попереду, одразу пробуємо відправити | неготовий (офлайн-машина) не тримає запис для всіх; готовий не обганяється пізнішим |
| 7 | Хто будить чергу на запис | кінець запуску будить машини запусків, що чекають ті самі записи; страховка — `sweep` раз на 30 с | так само, як машина |
| 8 | Скасування — API | `POST /executions/{id}/cancel`, `EXECUTION_CANCEL`: розробник і USER — свої запуски, адмін — будь-які (24-rbac). Повтор — без змін (200). Завершений — 409 | 24-rbac: «аварійна зупинка — за адміном теж» |
| 9 | Скасування в черзі | не відправлений → одразу `CANCELLED`, аудит `EXECUTION_CANCELLED` (актор — людина) | агент про нього не знає |
| 10 | Скасування відправленого / запущеного | `cancel_requested_at`, аудит `EXECUTION_CANCEL_REQUESTED`, `execution/cancel` агенту. Агент зупиняється на найближчій межі (між кроками, в очікуванні елемента, у `Delay`) і звітує `finished` `CANCELLED`, як звичайно. Агент не на зв'язку — `cancel` іде знову, коли він зареєструється. Статус лишається `RUNNING` до звіту; страховка — D51 (30 хв) | 09-protocol: «зупинити акуратно — після поточного кроку»; обірваний посеред кліку робот лишає сміття (D47) |
| 11 | «Немає зв'язку» (D51) | `executions.connection_lost_at`: ставиться відправленим і RUNNING-запускам, коли WS-з'єднання їхнього Assistant закрилось; знімається будь-яким звітом від нього і новою реєстрацією | D51: «RUNNING з позначкою "немає зв'язку"» |
| 12 | На що чекає запуск (D73) | `executions.waiting_reason` — результат некритичних перевірок; оновлюється, коли змінився, знімається при відправці. Studio показує «Чекає: …» | D73: видимість; раніше причину було видно лише в BLOCKED |
| 13 | Дозволені середовища — хто змінює | адмін: `PATCH /assistants/{id} { allowed_environments }` (непорожня підмножина `TEST`, `PROD`), аудит `ASSISTANT_UPDATED`, сповіщення `INFO`; черга машини перевіряється знову. Face: Settings → **Machines** | D76: «конфігурацією й політиками»; адмін — машини (24-rbac) |
| 14 | Assistant 1.3.0 | функції `parameters` і `cancel` у каталозі (`features`); версія з параметрами вимагає ≥ 1.3.0 (`min_assistant_version`). Протокол лишається 1: `input` — нове необов'язкове поле, `cancel` — нова дія | старий агент ігнорує `input`, але №12 не пустить до нього версію з параметрами |
| 15 | PROD-запуски й їхні перевірки (№5, 6, 9, 16 для PROD, 13) | **фаза 6**: PROD-запуск виконує лише Active Production Version (D40), а її ще немає. Порядок «PROD першим» у черзі вже працює | без активної версії PROD-запуску не існує |
| 16 | Дашборд Face: скільки чекає, найдовше очікування (D73) | разом із живими даними дашборду; зараз дашборд — зразок з Figma | окрема задача на весь дашборд |

Знайдено й виправлено під час прогону: у списку Runs попередній запуск лишався
`QUEUED`, коли стеження переходило на новий (список оновлювався лише для запуску,
за яким стежать) — тепер перед перемиканням останній стан записується в список.

UIA-тести десктопа падають, якщо поруч відкрите ще одне «Tekra test window» (кліки
потрапляють у нього) — не баг коду; прогін без зайвого вікна — 250 passed.

**Не перевірено живцем** (лише тестами на справжній БД): позначка «немає зв'язку»
в Studio — жорстке вбивство API не виконує `finally` з'єднання, а м'яко зупинити
uvicorn на Windows із цієї сесії не вдалося; черга на запис між двома **справжніми**
машинами — машина одна (перевірено гонкою й тестами з двома машинами в БД).
