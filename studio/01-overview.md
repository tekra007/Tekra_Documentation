# 1. Загальна картина

## Що ми будуємо

Зараз робота створює розробник **поза системою**: пише Python, пакує в ZIP,
юзер вручну ставить архів на десктоп.

Хочемо, щоб робота можна було **зібрати мишкою у браузері**, без програмування.

Три частини:

| Частина | Де живе | Що робить |
|---------|---------|-----------|
| **Studio** | веб (Face) | Редактор: юзер складає сценарій з кроків |
| **Inspector** | десктоп | Юзер тицяє на кнопку/поле в реальній програмі — система запам'ятовує, як її знайти |
| **Executor** | десктоп | Виконує готового робота |

Inspector і Executor — це **два режими одного десктоп-застосунку**, окремої
програми ставити не треба.

## Головна складність

Браузер **не бачить** вікна Windows. Він у пісочниці — не може навести курсор
на кнопку в 1С і сказати «оця кнопка».

Тому Studio у браузері мусить попросити десктоп зробити це за неї.

## Як вони спілкуються

Обговорювали два варіанти (деталі — [02-decisions.md](02-decisions.md), D5):

**Через оркестратор (обраний напрямок):**

```
   Браузер                   Оркестратор                 Десктоп
 ┌──────────┐               ┌───────────┐              ┌──────────┐
 │  Studio  │◄────WS───────►│  передає  │◄────WS──────►│ Inspector│
 └──────────┘               │ повідомл. │              └──────────┘
                            └───────────┘
```

Studio каже «обери елемент» → оркестратор передає десктопу → десктоп вмикає
режим підсвітки → юзер клікає на кнопку в потрібній програмі → назад летить
опис елемента і його скріншот.

Затримка тут не заважає: юзер сам не поспішає, а підсвітка під курсором
малюється **локально на десктопі** — у браузер вона не ходить.

Плюс так Studio можна відкрити на ноуті, а автоматизувати програму на
віддаленій VM.

## Хто за що відповідає

Найчастіша плутанина: «а бек Studio — це десктоп?». **Ні.** Бек Studio — це
оркестратор.

| Репозиторій | Роль у Studio | Що конкретно робить |
|-------------|---------------|---------------------|
| `Tekra-Orchester-Face` | **фронт Studio** | редактор: полотно, список кроків, форми налаштувань |
| `Tekra-Orchester` | **бек Studio** | зберігає роботів і версії, веде `jobs`, `machines`, логи; перевіряє сценарій; передає повідомлення між вебом і десктопом |
| `Tekra-Desktop` | **агент, не бек** | Inspector (зловити елемент) + Executor (виконати робота) |

### Studio — це назва функції, а не програми

Найчастіше питання після знайомства зі схемою: «то Studio живе в оркестраторі
чи у фронті?». Відповідь — **в обох**, і це не нова конструкція. У проєкті так
уже влаштоване все інше.

Подивись на **Ліцензії**:

| Частина | Де живе |
|---------|---------|
| сторінка `licenses` | `Tekra-Orchester-Face` |
| `routers/license.py`, `services/license_service.py`, модель `License` | `Tekra-Orchester` |

Ніхто не каже «ліцензії живуть в оркестраторі» або «ліцензії живуть у фронті».
Це **одна функція, розкладена по двох репозиторіях**: видима частина у фронті,
дані й логіка на бекенді.

Studio влаштована так само. Не окремий застосунок, не окремий сервіс.

| Що саме | Репозиторій |
|---------|-------------|
| редактор, список роботів, запуски, машини, розклади — **екрани** | `Tekra-Orchester-Face` → `pages/studio/` і сусідні |
| `/robots`, `/jobs`, `/machines`, `/credentials` — **API** | `Tekra-Orchester` → `routers/` |
| моделі БД, каталог активностей, валідація, планувальник | `Tekra-Orchester` → `models/`, `services/` |
| Inspector і Executor — **руки** | `Tekra-Desktop` |

> **Мозок у оркестраторі, обличчя у Face, руки в десктопі.**

### Аналогія

| | Хто це |
|---|---|
| **Face** | панель приладів, на яку дивишся |
| **Orchester** | мозок: памʼятає, роздає команди, веде облік |
| **Desktop** | руки: тільки він фізично тицяє в кнопки на екрані |

Десктоп нічого не зберігає й нічим не керує. Він виконує те, що прийшло, і
повідомляє результат.

### Чому бек не може жити в десктопі

Десктоп стоїть **на комп'ютері юзера**. У нього немає:

- бази даних, де живуть роботи всієї організації;
- доступу з браузера — саме тому в D5 вирішили ходити **через оркестратор**;
- багатокористувацькості: робот має бути видимий колегам (D8), а десктоп бачить
  лише себе;
- аптайму: юзер закрив ноутбук — і «бек» зник.

### Той самий потік по кроках

```
  Face (Studio)          Orchester              Desktop
  «обери елемент»  ──►   передав          ──►   підсвітив, юзер клікнув
  показав селектор ◄──   передав          ◄──   надіслав опис елемента

  «зберегти»       ──►   записав у БД
  «опублікувати»   ──►   створив версію
  «запустити»      ──►   створив Job      ──►   виконав, шле логи
  видно прогрес    ◄──   записав логи     ◄──
```

Усе, що зберігається й рахується — в оркестраторі. Десктоп власної памʼяті про
роботів не має.

### Де саме лежатиме код

Окремих репозиторіїв під Studio не заводимо (D15):

```
Tekra-Orchester-Face/src/app/pages/studio/   ← редактор, вантажиться ліниво
Tekra-Orchester/src/  routers|services|models ← API, БД, WS
Tekra-Desktop/src/    Inspector + Executor
```

## Життєвий цикл робота

```
 1. СТВОРЕННЯ     Studio: юзер складає кроки, ловить елементи через Inspector
                          │
 2. ПУБЛІКАЦІЯ    Робот заморожується у версію (RobotVersion) і лягає на сервер
                          │
 3. ЗАПУСК        Створюється завдання (Job): «виконати версію X на машині Y»
                  (у MVP машина — це комп'ютер залогіненого юзера)
                          │
 4. ДОСТАВКА      Оркестратор шле завдання агенту на машині Y
                          │
 5. ВИКОНАННЯ     Executor тягне пакет, виконує кроки
                          │
 6. ЗВІТ          Логи і статус летять назад в оркестратор → видно у вебі
```

## Словник

Щоб ми з тобою і агенти називали речі однаково.

| Термін | Що це |
|--------|-------|
| **Studio** | Веб-редактор роботів. Живе в `Tekra-Orchester-Face/` |
| **Robot** | Сценарій автоматизації. Опис у JSON, не код |
| **Activity** | Один крок сценарію: «клікнути», «ввести текст», «прочитати комірку» |
| **Selector** | Опис, як знайти елемент на екрані (вікно → панель → кнопка) |
| **Inspector** | Режим десктопа: захоплення елемента, на який тицьнув юзер |
| **Executor** | Режим десктопа: виконання робота крок за кроком |
| **Agent** | Сам десктоп-застосунок як ціле (Inspector + Executor) |
| **Machine** | Комп'ютер або VM, де стоїть Agent |
| **RobotVersion** | Заморожена, незмінна версія робота. Виконується завжди версія |
| **Job** | Одне завдання: виконати версію X на машині Y |
| **Attended** | Робот працює на машині, за якою сидить людина |
| **Unattended** | Робот працює сам на VM, без людини |
| **Активність** | Тип дії з каталогу: `desktop-uia/Click` |
| **Крок** | Конкретне вживання активності в цьому роботі, зі своїми параметрами |
| **Елемент** | Захоплений елемент екрана в бібліотеці робота |

Назви сутностей в інтерфейсі беруться **з моделі даних** (D29). Наявні підписи
у Face, що з ними розходяться, — застаріла чернетка й замінюються.

## Що вже є в системі (стан на 2026-08-20)

Це не «з нуля» — частина каркасу вже стоїть:

- десктоп ↔ оркестратор уже говорять по WebSocket (`/users/ws`);
- веб ↔ оркестратор — окремим каналом (`/admins/ws`);
- десктоп уміє ставити робота із ZIP і запускати його як Python-процес;
- у десктопі лежить власний Python 3.11 для роботів;
- у БД є `robots`, прив'язані до юзера.

**Чого немає:** поняття «машина». Таблиця `user_session` попри назву машиною не
є — це налаштування юзера (один рядок на юзера, створюється при реєстрації).
Тому сьогодні система не знає, на якому комп'ютері стоїть агент і де лежить
файл робота. Це виправляє рішення D3a.

Що доведеться змінити — у [02-decisions.md](02-decisions.md).
