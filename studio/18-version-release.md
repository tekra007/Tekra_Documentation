# 18. Release State версії

> Під ТЗ §4.1.2, §4.1.5, §4.1.15, §4.7.5. Закриває відкрите питання ТЗ **#23**.
> Рішення D39–D40 — ✅ прийнято 2026-09-17.

## Що каже ТЗ і де воно неоднозначне

ТЗ дає пʼять станів версії — DRAFT / TESTING / RELEASED / SUPERSEDED / REJECTED
(§4.1.5), але **не каже, коли версія переходить з одного в інший**. Саме тому
модель Release State винесена у відкрите питання #23.

Три місця, де без рішення не обійтись:

| Що в ТЗ | Чому незрозуміло |
|---------|------------------|
| §4.1.2 окремо фіксує, **хто виконав release** і **хто виконав approval** | отже release — це не те саме, що погодження. Але окремої кнопки «Release» у потоці Move to PROD (§4.1.15) немає |
| §4.7.5 перелічує для версії **три різні** події: release, promotion, production activation | треба зрозуміти, що кожна з них означає |
| §4.1.15, кроки 6 і 10: після погодження версія «**може стати** Active Production Version» | не «стає». Тобто активація може бути окремим кроком |

## Що означає кожна подія (D39 ✅)

| Подія ТЗ | Коли відбувається | Хто |
|----------|-------------------|-----|
| **створення** | «Зберегти» або автоматично перед запуском (D34) | розробник |
| **promotion** | розробник натиснув **Move to PROD** | розробник |
| **approval** | адмін погодив або відхилив запит (D38) | адмін |
| **release** | версія **отримала право працювати в PROD**: одразу після Move to PROD, якщо погодження не потрібне, або після APPROVE | фіксується **розробник, який подав** Move to PROD |
| **production activation** | вказівник Active Production Version переставлено на цю версію | система |
| **supersede** | попередня активна версія замінена іншою | система |
| **rollback** | вказівник повернули на стару версію | окремий блок |

Звідси `released_by_user_id` — це **розробник**, який подав версію в PROD, а не
адмін, що погодив. Адмін фіксується окремо — у `approvals.decided_by_admin_id`.
Так виконується вимога ТЗ §4.1.2: release і approval — різні люди й різні події.

## Переходи між станами (D39 ✅)

```
   «Зберегти» / автоматично перед запуском (D34)
                 │
                 ▼
               DRAFT ─── перший TEST-запуск цієї версії ───► TESTING
                 │                                              │
                 └────────────────── Move to PROD ──────────────┤
                                                                 │
                                        ┌────────────────────────┴───────────┐
                              погодження не потрібне              погодження потрібне
                                        │                                    │
                                        │                    стан версії не змінюється,
                                        │                    authorization = PENDING_APPROVAL
                                        │                              ┌─────┴─────┐
                                        │                           APPROVE      REJECT
                                        │                              │            │
                                        ▼                              ▼            ▼
                                     RELEASED ◄────────────────────────┘        REJECTED
                                        │
                     в PROD активували іншу версію
                                        ▼
                                   SUPERSEDED
```

| Стан | Що означає | Хто ставить |
|------|------------|-------------|
| `DRAFT` | версію збережено, ще жодного разу не запускали | система при створенні |
| `TESTING` | версію хоч раз запускали в TEST | система при першому TEST-запуску |
| `RELEASED` | версія отримала право працювати в PROD | система після Move to PROD (+ APPROVE, якщо потрібне) |
| `SUPERSEDED` | була в PROD, її замінила інша версія | система при активації іншої версії |
| `REJECTED` | адмін відхилив запит на PROD | система після REJECT |

**`TESTING` ставиться автоматично**, без окремої кнопки. Так одразу видно, які
версії справді запускали, а які лише зберегли.

**У PROD можна подати й версію в стані `DRAFT`** — ТЗ цього не забороняє. Але
валідація (D14) показує **попередження**: «цю версію жодного разу не запускали в
TEST».

### Як це узгоджується з Authorization (D36)

Це два різні виміри ТЗ, і в двох точках вони змінюються **однією подією**:

| Подія | `release_state` | `authorization` |
|-------|-----------------|-----------------|
| збереження | DRAFT | порожньо — на PROD не подавали |
| перший TEST-запуск | TESTING | порожньо |
| Move to PROD, погодження не потрібне | RELEASED | NOT_REQUIRED |
| Move to PROD, погодження потрібне | без змін | PENDING_APPROVAL |
| APPROVE | RELEASED | APPROVED |
| REJECT | REJECTED | REJECTED |

## Активувати одразу після release чи окремою дією (D40 ✅)

ТЗ каже: після погодження версія «**може стати**» активною, і окремо перелічує
подію production activation.

| | Варіант | Плюси | Мінуси |
|---|---------|-------|--------|
| A | **одразу**: RELEASED → вказівник Active Production Version переставляється в ту ж мить | один крок; нічого не треба памʼятати | немає способу погодити вдень, а ввімкнути вночі |
| B | **окремою дією**: RELEASED — версія лише «готова»; активує розробник або адмін кнопкою | повний контроль моменту перемикання | ще одна кнопка; легко погодити й забути ввімкнути |

**Рішення — A для MVP.** Модель даних уже розділяє ці речі: стан живе на
версії, вказівник — на роботі. Тому перейти на B пізніше можна без міграції
даних — достатньо перестати переставляти вказівник автоматично.

## Що свідомо не вирішуємо тут

> Оновлено: обидва питання нижче розібрано в
> [23-rollback-archive.md](23-rollback-archive.md) — D53 і D54.

**Rollback** (питання ТЗ #2, #4, #5, #6). Схема вище показує лише, як змінюється
стан, якщо повернутись на стару версію: стара `SUPERSEDED` → `RELEASED`, поточна
→ `SUPERSEDED`. Але чи потрібне для цього нове погодження, хто має право його
робити і чи лишається стара версія `APPROVED` — окремий блок.

**Повторна подача відхиленої версії.** Чи можна знову подати в PROD версію в
стані `REJECTED` без змін (наприклад, адмін відхилив лише через невдалий час)?
ТЗ мовчить. Невелике питання, повернемось разом із rollback.
