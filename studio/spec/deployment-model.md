**Єдина deployment-модель платформи** - з двома режимами розгортання для клієнтів, але з однією продуктовою архітектурою:

```
                    ┌──────────────────────────┐
                    │       MARKETPLACE        │
                    │       GLOBAL / ONE       │
                    │                          │
                    │  Components              │
                    │  Automations / Robots    │
                    │  Processes / Templates   │
                    │  Connectors              │
                    └────────────┬─────────────┘
                                 │
                    distribute / install / update
                                 │
            ┌────────────────────┴───────────────────┐
            ▼                                        ▼
   ┌──────────────────────┐              ┌──────────────────────┐
   │     FREE / TRIAL     │              │  PAID / ENTERPRISE   │
   │  SHARED ENVIRONMENT  │              │ ISOLATED DEPLOYMENT  │
   └──────────┬───────────┘              └──────────┬───────────┘
        ┌─────┼─────┐                     ┌─────────┴─────────┐
        ▼     ▼     ▼                     ▼                   ▼
   Tenant A Tenant B Tenant C        Customer A          Customer B
        └─────┼─────┘                     │                   │
              ▼                           ▼                   ▼
      ┌───────────────┐          ┌──────────────┐    ┌──────────────┐
      │ Shared Studio │          │    Studio    │    │    Studio    │
      │ Shared Orch.  │          │      +       │    │      +       │
      │ Shared Infra  │          │ Orchestrator │    │ Orchestrator │
      └───────┬───────┘          │  Customer A  │    │  Customer B  │
              │                  └──────┬───────┘    └──────┬───────┘
        ┌─────┴─────┐               ┌───┴───┐           ┌───┴───┐
        ▼           ▼               ▼       ▼           ▼       ▼
    Assistant   Assistant     Assistant Assistant Assistant Assistant
    Machine A   Machine B       PC-01     PC-02     PC-01    Server
```

## 1. Marketplace - один і глобальний

Marketplace **не прив'язаний до конкретного клієнта**.

Він є єдиним каталогом:

- компонентів;
- Composite Components;
- Automation / Robots;
- Business Tasks;
- Processes / шаблонів;
- Connectors;
- інших артефактів, які ви вирішите розповсюджувати.

Клієнт знаходить артефакт у Marketplace і встановлює/імпортує його у своє середовище.

## 2. Free / Trial - shared

Для безкоштовного доступу **не створюємо окремий deployment на кожного користувача**. Маємо:

```
                 FREE / TRIAL PLATFORM
                          │
        ┌─────────────────┼─────────────────┐
     Tenant A          Tenant B          Tenant C
        └─────────────────┼─────────────────┘
                          │
                    Shared Studio
                 Shared Orchestrator
                Shared Infrastructure
```

Але кожен Tenant **логічно ізольований**:

- свої користувачі;
- свої ролі;
- свої процеси;
- свої Business Tasks;
- свої Automations;
- свої компоненти/налаштування;
- свої credentials;
- свої execution;
- свої логи;
- свої дані.

**Tenant A не бачить Tenant B.**

При цьому фізично вони можуть працювати на спільному cloud infrastructure.

Free/Trial просто має обмеження:

- ліміти execution
- ліміти concurrent jobs
- ліміти storage
- ліміти кількість Assistant
- ліміти доступні функції
- ...

## 3. Paid / Enterprise - isolated

Коли клієнт переходить на платний рівень, він отримує **власний deployment**.

```
Customer A
│
├── Studio
├── Orchestrator
├── Database
├── Queue / Cache
├── Configuration
├── Secrets / Credentials
└── Logs / Execution data
```

А інший клієнт:

```
Customer B
│
├── Studio
├── Orchestrator
├── Database
├── Queue / Cache
├── Configuration
├── Secrets / Credentials
└── Logs / Execution data
```

Фізично це все може знаходитися:

```
AWS
│
├── Customer A deployment
├── Customer B deployment
├── Customer C deployment
└── ...
```

або в Azure / GCP / іншій інфраструктурі.

Тобто **окремий deployment ≠ окремий фізичний сервер**.

## 4. Studio + Orchestrator

Важливо!!! Архітектурне розділення!

Для користувача: **Customer Deployment = Studio + Orchestrator**

Але технічно це не обов'язково один Docker container.

Наприклад:

```
Customer A Deployment
│
├── Studio
│     ├── container
│     └── container ...
│
├── Orchestrator
│     ├── API container
│     ├── Scheduler container
│     ├── Worker container
│     └── ...
│
├── DB
└── supporting services
```

Тобто **ізольований deployment - це одиниця розгортання клієнта**, а не обов'язково один контейнер. Docker/Kubernetes дозволять потім масштабувати його без зміни продуктової моделі.

## 5. Assistants - окремий рівень

Assistant **не входить у deployment Studio/Orchestrator як звичайний container**.

Він встановлюється туди, де фактично має виконуватися автоматизація:

```
Customer A Deployment
        │
        ├───────────────────┐
        ▼                   ▼
    Assistant           Assistant
   Windows PC        Windows Server
        │                   │
        ▼                   ▼
      Apps                Apps
      BAS                 Browser
      Excel               Files
      etc.                etc.
```

Assistant реєструється у відповідному Orchestrator.

Наприклад:

```
Assistant #27
   ↓
Customer A
   ↓
PROD
   ↓
Machine "Accounting-PC-01"
```

## 6. Перехід: Free → Paid

Це має бути **не міграція в інший продукт**, а зміна deployment model.

```
   FREE / TRIAL
        │
     Tenant A
        │
    "Upgrade"
        │
        ▼
┌─────────────────────┐
│ Customer A          │
│ isolated deployment │
└─────────────────────┘
```

Тобто клієнт зберігає:

- акаунт;
- свої процеси;
- свої Automation;
- свої компоненти;
- свої налаштування;
- свої дані - в межах того, що дозволяє тариф/політика міграції.

А інфраструктура переходить із: **Shared → Isolated.**

## 7. Спрощена загальна модель

**Архітектурний принцип**: платформа складається з єдиного глобального Marketplace та клієнтських середовищ, які можуть працювати у **shared multi-tenant режимі** для Free/Trial або як **ізольовані deployment'і** для **платних та Enterprise-клієнтів**; кожне клієнтське середовище містить **Studio** та **Orchestrator**, а **Assistant** встановлюється окремо на машинах, де виконується автоматизація.

І якщо зовсім коротко, пропонована базова deployment-архітектура:

```
                     PLATFORM
                         │
          ┌──────────────┴──────────────┐
     MARKETPLACE                CUSTOMER ENVIRONMENTS
     ONE / GLOBAL                       │
                               ┌────────┴────────┐
                             FREE              PAID
                            SHARED           ISOLATED
                               │                 │
                          Many Tenants      One Customer
                               │                 │
                         Studio + Orch.    Studio + Orch.
                               └────────┬────────┘
                                        │
                                    ASSISTANTS
                                        │
                                  REAL MACHINES
```

### 1. Business Tasks і Connectors

**Business Tasks** - це окрема бізнес-сутність, яка реалізується через BPMN Task. Це як раз ті самі «квадратики» в BPMN. Тобто, задача яку виконує людина, робот (робот винесений окремо, але по факту він теж є виконавцем бізнес-задачі) або щось інше. Типу такого:

```
Business Process (BPMN)
   │
   ├── Business Task
   │     │
   │     ├── Виконавець: людина / AI / зовнішня система
   │     │
   │     └── Виконавець: Automation / Robot
   │                         │
   │                         └── Components
   │
   └── Інші елементи BPMN
         Events / Gateways / Flows / Subprocesses
```

Крім того, в середині такого «квадратика» можуть «жити» окремі бізнес-задачі. Тобто, він складається з бізнес-підзадач (в BPMN можливі вкладеності). Але наразі достатньо першого: бізнес таска - це якась завершена бізнес дія, яку виконує людина/робот/ШІ тощо і яка на BPMN відображається у вигляді «квадратика».

**Connectors** - інтеграційний платформи, який забезпечує взаємодію із зовнішньою системою, сервісом або джерелом даних. Залежно від підтримуваних можливостей, взаємодія може здійснюватися через API, бази даних, файловий обмін, поштові й повідомлювальні сервіси або інші механізми. UI-автоматизація та взаємодія з операційною системою також підтримуються платформою, але не обов'язково мають моделюватися як окремі Connector. Конкретний спосіб виконання визначається відповідними компонентами та механізмами виконання.

### 2. Marketplace

Потрібно передбачити три категорії авторів:

1. **Власник платформи** - публікує офіційні компоненти, конектори, автоматизації, шаблони тощо.
2. **Партнери/розробники** - можуть публікувати власні артефакти після виконання вимог Marketplace.
3. **Клієнти** - купують опубліковані артефакти.

В моделі Marketplace, окрім іншого, потрібно також виділити три незалежні поняття:

1. **Автор** - хто створив артефакт
2. **Видимість** - хто може його бачити та використовувати
3. **Модель поширення** - безкоштовно, платно або лише для внутрішнього використання

Не кожен артефакт, створений у Studio, повинен автоматично потрапляти в глобальний каталог.

**Чи можуть артефакти бути платними?**

Так, необхідно передбачити платні артефакти архітектурно, навіть якщо монетизація не увійде до першого релізу. Наприклад:

- безкоштовні компоненти;
- платні компоненти;
- готові автоматизації для типових бізнес-сценаріїв;
- галузеві пакети;
- комерційні інтеграції.

Це дасть можливість розвивати екосистему розробників і партнерів.

**Чи має Enterprise доступ до Marketplace без інтернету?**

Тут потрібно передбачити два сценарії.

**Онлайн:** ізольований deployment має можливість звертатися до глобального Marketplace, якщо мережеві політики клієнта це дозволяють.

**Закритий контур:** клієнт отримує можливість імпортувати підписані пакети вручну або через контрольований механізм перенесення.

Наприклад:

```
GLOBAL MARKETPLACE
   ↓
Download package
   ↓
Customer's controlled environment
   ↓
Validate package
   ↓
Import into Studio
   ↓
Test → Approve → Deploy
```

Для закритого контуру Marketplace не повинен бути обов'язковою онлайн-залежністю для виконання вже встановлених процесів і автоматизацій. Для закритих середовищ необхідний контрольований імпорт пакетів з глобального Marketplace.

### 3. Хто обслуговує deployment

Не обмежувати архітектуру лише хмарою під управлінням TEKRA. Потрібно передбачити customer-managed deployment (в нашій хмарі/хмарі клієнта/на серверах клієнта в його приміщенні), навіть якщо на першому етапі підтримуватиметься тільки керований cloud. Тобто, 2 варіанти:

- Cloud deployment під управлінням TEKRA
- Customer-managed deployment

### 4. Assistant

Assistant повинен мати власний стабільний ідентифікатор, окремий від ідентифікатора машини.

Наприклад:

```
Organization: Customer A

Machine:
  ID: MACHINE-27
  Name: Accounting-PC-01

Assistant:
  ID: ASSISTANT-104
  Machine: MACHINE-27
  Status: Online
```

Це дає змогу ідентифікувати агент, контролювати його стан і керувати його реєстрацією незалежно від назви машини.

**Чи може на одній машині працювати кілька Assistant?**

Я б не дозволяв це як стандартну конфігурацію без визначених правил. Один Assistant на машині - простіша базова модель для UI-автоматизації, оскільки кілька агентів можуть конфліктувати за робочий стіл, клавіатуру, мишу, сесію користувача та ресурси.

Якщо згодом виникне потреба в кількох Assistant на одній робочій машині/сервері, потрібно буде окремо визначити підтримуваний сценарій, наприклад різні ізольовані користувацькі сесії.

*Але, одна машина не обов'язково дорівнює одній сесії або одному environment'у.*

**Чи прив'язується Assistant до PROD або TEST?**

Потрібно розділити (розрізняти) реєстрацію Assistant'а та призначення його для виконання.

Assistant реєструється в конкретному Orchestrator і прив'язується до машини. А можливість виконувати роботи в певному середовищі визначається окремою конфігурацією та політиками.

Наприклад:

```
Assistant #104
   │
   ├── Organization: Customer A
   ├── Machine: Accounting-PC-01
   └── Allowed environments:
         ├── TEST
         └── PROD
```

Це узгоджується з принципом, що один Assistant може використовуватися і для TEST, і для PROD, якщо така конфігурація дозволена.

Однак для критичних продуктивних середовищ можуть бути потрібні суворіші обмеження, наприклад окремі машини для TEST і PROD.

**Коротко:** Assistant має власний ID, Machine має власний ID, а Environment - окремий контекст виконання. Не варто ототожнювати їх або жорстко прив'язувати Assistant до одного середовища на рівні самої сутності.

### 5. Free → Paid

Free → Paid - це перенесення клієнтського середовища зі shared deployment в isolated deployment зі збереженням бізнес-артефактів та необхідної історії.

Але не обов'язково копіювати абсолютно всі технічні дані.

**Що переносимо**

| Дані | Рекомендація |
|---|---|
| Акаунти та користувачі | Переносимо або прив'язуємо до глобального акаунта |
| Організація / Tenant | Зберігаємо ідентичність організації |
| Процеси | Переносимо |
| Business Tasks | Переносимо |
| Automations / Robots | Переносимо |
| Компоненти та конфігурації | Переносимо |
| Версії артефактів | Переносимо |
| Змінні й налаштування | Переносимо |
| Credentials / Secrets | Переносимо через безпечне перешифрування |
| Історія виконань | Переносимо в межах визначеної політики зберігання |
| Аудит | Переносимо в межах визначеної політики зберігання |

Особливо важливо зберегти зв'язки між процесами, роботами, версіями та їхніми execution.

**Можливий сценарій міграції**

```
SHARED FREE ENVIRONMENT
   ↓
Export tenant data
   ↓
Validate dependencies
   ↓
Import into isolated deployment
   │
   ├── Re-encrypt secrets
   ├── Restore configurations
   ├── Restore artifact versions
   └── Restore permitted history
   ↓
Re-register / reconnect Assistants
   ↓
Validate → Activate
```

І так, для міграції потрібно враховувати обидві бази даних - Studio та Orchestrator. Тому що перенесення лише однієї з них може залишити артефакти без пов'язаних execution'ів або конфігурацій.

**Що робити з Tenant у Free?**

Після успішної міграції його потрібно перевести в стан, у якому він більше не запускає автоматизації у shared-середовищі.

Як на мене, краще не видаляв його відразу. Проте:

- зберегти ідентифікатор Tenant;
- позначити його як мігрований;
- припинити виконання в старому середовищі;
- зберегти можливість аудиту й відновлення в межах визначеного терміну;
- після завершення періоду зберігання видалити зайві дані відповідно до політики (опишемо окремо).

Це захищає від ситуації, коли після міграції один і той самий процес випадково запускається і в Free, і в Paid. І дає можливість швидко відкотити назад.

**Чи можливий зворотний перехід Paid → Free?**

Наразі не робити зворотний перехід (автоматичний/ручний - будь-який). Технічно він можливий(?), але потребуватиме перевірки/узгодження лімітів на Free, перенесення даних, обробки credentials, історії та конфліктів версій.

Тому:

- Free → Paid - продуктовий сценарій;
- Paid → Free - окреме майбутнє рішення.

### 6. Акаунт

Я за глобальний акаунт платформи плюс локальні права доступу в кожному deployment. За розподіл на такі собі два різних рівні.

**Глобальний акаунт**

Ідентифікує користувача в межах платформи та може використовуватися для:

- входу;
- Marketplace;
- підписок і оплати;
- керування організаціями;
- переходу Free → Paid.

**Локальна авторизація**

Визначає, що користувач може робити в конкретному середовищі:

- редагувати процеси;
- створювати автоматизації;
- запускати роботи;
- переглядати логи;
- керувати користувачами;
- адмініструвати Orchestrator.

Приклад:

```
GLOBAL ACCOUNT
  User #123
    │
    ├── Marketplace
    │
    ├── Organization A
    │     ├── Studio
    │     └── Orchestrator
    │
    └── Organization B
          ├── Studio
          └── Orchestrator
```

Користувач може бути учасником кількох організацій, якщо йому надали відповідний доступ.

При цьому глобальний акаунт не повинен автоматично давати права адміністратора в усіх клієнтських deployment.

Інакше під час переходу Free → Paid доведеться створювати новий акаунт або вручну переносити ідентичність користувача (хоча, може я помиляюсь?).

Глобальний акаунт дозволяє зберегти ідентичність, тоді як права доступу до конкретного середовища керуються окремо.

Для ізольованих enterprise-клієнтів, які працюють у закритому контурі, потрібно передбачити локальну автентифікацію або інтеграцію з корпоративним Identity Provider'ом. Але це не скасовує глобальної моделі акаунтів для загальнодоступної платформи.

**Коротко:** глобальна ідентичність користувача - на рівні платформи; ролі та права - на рівні організації і deployment.

### 7. Версії

Має сенс розрізняти **версію продукту** та **версію встановленого deployment'а**.

Продукт має єдину кодову базу, але це не означає, що всі клієнти повинні оновлюватися одночасно.

**Пропонована модель**

```
          PRODUCT RELEASES
                │
      ┌─────────┼─────────┐
    v1.4      v1.5      v1.6
      ↓         ↓         ↓
 Customer A Customer B Customer C
    v1.4      v1.5      v1.6
```

Кожен deployment має власну зафіксовану версію.

Наприклад:

- Customer A залишається на v1.4, оскільки, наприклад, проводить внутрішнє тестування;
- Customer B переходить на v1.5;
- Customer C використовує v1.6.

Це дасть змогу контролювати rollout і зменшити ризик одночасного впливу невдалого релізу на всіх клієнтів.

**Як це має виглядати?**

1. TEKRA випускає нову версію платформи.
2. Версія проходить внутрішнє тестування.
3. Оновлення стає доступним для відповідних deployment'ів.
4. Оновлення застосовується за визначеною політикою.
5. Після оновлення перевіряється працездатність.
6. За потреби виконується rollback, якщо це технічно підтримується конкретним типом змін.

Для Free/Trial - встановити централізоване автоматичне оновлення спільного середовища.

Для Paid/Enterprise:

- автоматичні оновлення за погодженою політикою;
- керовані оновлення;
- можливість відкласти оновлення в межах підтримуваного періоду;
- окремі правила для on-premises.

**Marketplace**

Тут пропоную розділяти версію платформи та версії артефактів.

Оновлення платформи не повинно непомітно перезаписувати встановлені компоненти чи роботів. Артефакти мають версіонуватися незалежно.

**Коротко:** deployment можуть мати різні версії платформи, але всі вони походять з єдиної кодової бази. Free/Trial оновлюється централізовано, Paid/Enterprise - відповідно до політики оновлень конкретного deployment.
