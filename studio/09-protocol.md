# 9. Протокол: HTTP чи WebSocket

> Чернетка. Перелік повідомлень уточниться при реалізації.

## Правило, за яким обираємо

Просте й працює майже завжди:

| | Коли | Приклад |
|---|------|---------|
| **HTTP** | клієнт знає, що йому треба, і питає сам | «дай список роботів» |
| **WebSocket** | сервер має сам штовхнути те, чого клієнт не чекав, або йде потік подій | «крок 7 виконано», «машина відключилась» |

Дві типові помилки:

- **усе по WS.** У WebSocket немає ані кешування, ані статус-кодів, ані
  повторів. Кожен запит доводиться самому звʼязувати з відповіддю через
  `request_id`. HTTP дає це безкоштовно.
- **логи по HTTP-опитуванню.** Один запит на секунду × кожен відкритий екран —
  і сервер лягає на рівному місці.

## Як це лягає на Studio

| Що | Канал | Чому |
|----|-------|------|
| каталог активностей (D2) | HTTP | майже статика, тягнеться раз при відкритті, кешується |
| список роботів, версій, машин | HTTP | звичайний запит-відповідь |
| зберегти чернетку | HTTP | треба знати результат збереження |
| опублікувати версію | HTTP | створення ресурсу |
| запустити робота | HTTP `POST` | повертає `job_id` |
| **прогрес виконання** | WS | сервер штовхає події сам |
| **логи кроків** | WS | потік |
| **сесія Inspector'а** | WS | живий двонаправлений діалог |
| статус машини онлайн/офлайн | WS | подія |

Face уже має канал `/admins/ws` — Studio додає до нього підписки, а не новий
канал.

## Три ноги

```
   Face  ──HTTP──►  Orchester
   Face  ◄──WS───►  Orchester        (/admins/ws — уже є)
                        │
                        ▼
   Desktop ◄──WS───► Orchester        (/users/ws — уже є, D5)
```

## Повідомлення Desktop ↔ Orchester

### Реєстрація машини (D3a, D9, D10)

| Напрямок | Повідомлення | Вміст |
|----------|--------------|-------|
| → сервер | `MACHINE_REGISTER` | `machine_key`, `name`, `os`, `agent_version`, `capabilities` |
| ← сервер | `MACHINE_REGISTERED` | `machine_id` |

`capabilities` — які провайдери вміє цей агент. Studio за ними розуміє, чи можна
на цій машині захопити елемент у браузері.

### Inspector

| Напрямок | Повідомлення | Вміст |
|----------|--------------|-------|
| → агент | `INSPECT_START` | `session_id`, `provider` |
| → агент | `INSPECT_CANCEL` | `session_id` |
| ← агент | `INSPECT_RESULT` | селектор, знімок захоплення (D7a), скріншот елемента |
| ← агент | `INSPECT_FAILED` | причина |

### Виконання

| Напрямок | Повідомлення | Вміст |
|----------|--------------|-------|
| → агент | `JOB_ASSIGN` | `job_id`, сценарій версії, вхідні параметри |
| ← агент | `JOB_ACCEPTED` | `job_id` — переводить статус `SENT` → `RUNNING` |
| ← агент | `JOB_PROGRESS` | `step_id`, стан кроку |
| ← агент | `JOB_LOG` | пачка рядків логу |
| ← агент | `JOB_FINISHED` | результат, `output`, `error_message` |
| → агент | `JOB_STOP` | зупинити |

## Ухвалено (D26 ✅, D27 ✅)

**Логи** їдуть пачками, але повідомлення рівня `ERROR` надсилається негайно.
Юзеру важливо миттєво побачити, коли зламалось, а не кожен успішний крок.

**Прогрес** отримує лише той, хто підписався на конкретний `job_id`. Інакше при
тридцяти роботах кожна відкрита вкладка тоне в чужих подіях.
