# 9. Протокол: канали й повідомлення

> Чернетка, перелік повідомлень уточниться при реалізації. Переписано
> 2026-10-05 під ТЗ і D31 (Studio — окремий сервіс). HTTP-ендпоінти —
> [13-api.md](13-api.md); повідомлення між Studio й оркестратором —
> [28-studio-service.md](28-studio-service.md).

## Канали

```
    Studio-front                                         Face
      │ HTTP          └──────── HTTP + WS ────────┐        │ HTTP + WS
      ▼                                           ▼        ▼
  Studio-back  ◄═══ RabbitMQ (FastStream) ═══►  Оркестратор  ◄─── WS ───  Десктоп
                                                            (/users/ws, D5)
```

| Канал | Що ходить | Де описано |
|-------|-----------|------------|
| Studio-front → Studio-back, HTTP | редагування: робоча копія, версії, компоненти, процеси, каталог, перевірка | [13-api.md](13-api.md) |
| Studio-front ↔ оркестратор, HTTP + WS | тестові запуски, логи наживо, Inspector, Move to PROD, стани роботів | [13-api.md](13-api.md), нижче |
| Face ↔ оркестратор, HTTP + WS | адмін-панель: погодження, політики, аудит, машини; запуск PROD для Regular User | [13-api.md](13-api.md), нижче |
| Studio ↔ оркестратор, брокер | події «робота / версію створено» тощо, запит-відповідь для перевірок | [28-studio-service.md](28-studio-service.md) |
| оркестратор ↔ десктоп, WS | реєстрація машини, Inspector, виконання | нижче |

Studio з десктопом не говорить ніколи (ТЗ §4.8, D5). У десктопа рівно одне
зʼєднання — `/users/ws`.

## Правило, за яким обираємо HTTP чи WS

| | Коли | Приклад |
|---|------|---------|
| **HTTP** | клієнт знає, що йому треба, і питає сам | «дай список роботів», «запусти» |
| **WebSocket** | сервер має сам штовхнути те, чого клієнт не чекав, або йде потік подій | «крок 7 виконано», «машина відключилась» |

Дві типові помилки:

- **усе по WS.** У WebSocket немає ні кешування, ні статус-кодів, ні повторів —
  кожен запит доводиться самому звʼязувати з відповіддю через `request_id`. HTTP
  дає це безкоштовно;
- **логи HTTP-опитуванням.** Запит щосекунди × кожен відкритий екран — і сервер
  лягає на рівному місці.

## Браузер ↔ оркестратор: події по WS

Face уже має канал `/admins/ws` — події для адмін-панелі додаються до нього.
Studio-front (розробники, не адміни) теж отримує події з оркестратора — логи
наживо, Inspector, «версію зареєстровано» (D82). Чи це той самий канал з
перевіркою ролі, чи окремий шлях — уточнити при реалізації разом із входом через
Keycloak (D81).

| Подія | Кому |
|-------|------|
| прогрес запуску, пачки логів | лише тим, хто підписався на конкретний `execution_id` (D27) |
| `EXECUTION_PAUSED` — крок і змінні без облікових даних | тому, хто налагоджує (D66) |
| результат Inspector | тому, хто відкрив сесію; браузер сам кладе елемент у робочу копію через Studio (D31) |
| машина онлайн / офлайн | усім, хто дивиться список машин |
| версію зареєстровано | автору версії — щоб увімкнути «Запустити» (D68) |
| сповіщення адмінам | як уже працює (`admin_notifications`) |

Фаза 1 (L5, D90) — канал `/me/ws`:

| Напрямок | Повідомлення | Вміст |
|----------|--------------|-------|
| → сервер | `subscribe_execution` / `unsubscribe_execution` | `execution_id`; дозволено, коли дозволено `GET /executions/{id}` |
| ← сервер | `execution_subscribed` | `execution` — запуск як він є зараз |
| ← сервер | `execution_updated` | `execution` — після кожної зміни (статус, часи доставки, результат) |
| ← сервер | `execution_logs` | `execution_id`, `entries[]` — пачка, як надіслав Assistant (`ERROR` — одразу) |
| ← сервер | `version_registered` | `robot_id`, `version_number` — лише автору версії |
| ← сервер | `error` | `detail`, інколи `execution_id` |

Події йдуть лише після коміту й між процесами — через fanout-обмін брокера
(`orchestrator.browser`); доставка best effort: після (пере)підключення браузер
підписується знову й дочитує стан і логи по HTTP (`after_seq`).

## Оркестратор ↔ десктоп

### Реєстрація Assistant і машини (D76, D77, D10)

| Напрямок | Повідомлення | Вміст |
|----------|--------------|-------|
| → сервер | `ASSISTANT_REGISTER` | `assistant_key`, `machine_guid`, `machine_name`, `os`, `agent_version`, `protocol_version`, `capabilities` |
| ← сервер | `ASSISTANT_REGISTERED` | `assistant_id`, `machine_id`, номери `ASSISTANT-104` / `MACHINE-27`, дозволені середовища |

У WS це `command: "assistant"`, `action: "register"` / `"registered"` (L3).
Новий Assistant без посилання підключення отримує лише `TEST`; з посиланням — середовища,
які адмін дозволив у ньому (D87).

`protocol_version` — щоб оркестратор знав, чи підтримує цей Assistant (deployment
оновлюються окремо від ПК, D74).

`capabilities` — які провайдери вміє агент (з фази 2 — і `flow`: змінні, `If`,
`ForEach`, `TryCatch`; Assistant фази 1 його не має). За ними перевіряється сценарій
(D14, через запит Studio → оркестратор) і перевірка №12 перед запуском.

### Inspector

| Напрямок | Повідомлення | Вміст |
|----------|--------------|-------|
| → агент | `INSPECT_START` | `session_id`, `provider` |
| → агент | `INSPECT_CANCEL` | `session_id` |
| ← агент | `INSPECT_RESULT` | селектор, знімок захоплення (D7a), скріншот елемента. Оркестратор пересилає в браузер і не зберігає |
| ← агент | `INSPECT_FAILED` | причина |

У WS це `command: "inspector"` (фаза 3, [35](35-phase-3.md)): `start` —
`session_id`, `provider`, `timeout_seconds`; `cancel` — `session_id`, `reason`;
`result` — `session_id`, `element` (`strategies`, `label`, `snapshot` із
`image` — PNG data URL); `failed` — `session_id`, `reason`. Відповідь приймається
лише від Assistant сесії, лише поки вона відкрита; `element` перевіряється за
контрактом (≤ 256 KiB). У браузер — `/me/ws` власнику сесії: `inspector_result`
(`session_id`, `element`) або `inspector_failed` (`session_id`, `reason`).

### Виконання

| Напрямок | Повідомлення | Вміст |
|----------|--------------|-------|
| → агент | `EXECUTION_ASSIGN` | `execution_id`, `robot_id`, `version_number`, показ `184.2` для логів агента, `lifecycle: TEST \| PROD` (§4.8), **повний** `definition` версії разом із вмістом компонентів (D64), вхідні параметри, `scope` (D66), розшифровані значення облікових даних (D20) |
| ← агент | `EXECUTION_ACCEPTED` | агент отримав — `delivered_at`; оркестратор раніше ставить `dispatched_at` (D35) |
| ← агент | `EXECUTION_PROGRESS` | `step_id`, стан кроку |
| ← агент | `EXECUTION_LOG` | пачка рядків логу |
| ← агент | `EXECUTION_PAUSED` | на якому кроці, змінні без облікових даних (D66) |
| ← агент | `EXECUTION_FINISHED` | `COMPLETED` / `FAILED` / `CANCELLED`, `result`, `error` |
| → агент | `EXECUTION_PAUSE` / `EXECUTION_RESUME` | пауза й продовження (§4.1.18) |
| → агент | `EXECUTION_STEP` | один крок і знову пауза (D66) |
| → агент | `EXECUTION_CANCEL` | зупинити акуратно — після поточного кроку |
| → агент | `EXECUTION_TERMINATE` | обірвати негайно (D51) |

У WS це `command: "execution"`, дії `assign` (→ агент) і `accepted` / `log` /
`finished` (← агент) (L4). Фаза 8C: `assign` + `scope`; ← `paused` (`execution_id`, `step_id`, `variables` — лише живою подією, не в БД); → `resume` (`execution_id`, `step`). Фаза 7: `definition` в `assign` — без `triggers` (розклад — справа оркестратора). Фаза 1: `assign` — `execution_id`, `robot_id`,
`robot_number`, `version_number`, `label` (`184.2`), `lifecycle`, `definition`;
`log` — `execution_id`, `entries[]` (`seq`, `step_id`, `level` `INFO` / `WARN` /
`ERROR`, `message`, `occurred_at`, `payload`), до 500 рядків; `finished` —
`execution_id`, `status`, `result`, `error`, `steps_total`, `steps_done`,
`errors_count`, `fallbacks_count` (6C: скільки елементів знайдено резервним способом,
D7a — WARNING Health, D52; старі Assistant не шлють — 0). Звіт приймається лише від Assistant, якому запуск відправили.
Не підтвердив за 60 с — `FAILED`, повторно не шлемо (міг отримати).

**Фаза 5 (Assistant 1.3.0, протокол лишається 1):**

- `assign.input` — значення параметрів (D22), на старті — змінні (`{{file}}`).
  Старий агент поле ігнорує, але версія з параметрами вимагає 1.3.0 (№12).
- `cancel` (→ агент) — `execution_id`, `reason`. Запуск у черзі агента знімається
  одразу (`finished` `CANCELLED`, 0 кроків); той, що виконується, зупиняється на
  межі кроку, в очікуванні елемента чи в `Delay` і звітує `finished` `CANCELLED` з
  `error = reason`. У кожного запуску своя зупинка — скасування одного не чіпає
  наступних. Агент не на зв'язку — `cancel` іде знову після `assistant/registered`.
- Закрилося WS-з'єднання агента, а інших немає — його відправлені й RUNNING-запуски
  отримують `connection_lost_at`; будь-який звіт від агента або нова реєстрація
  знімає позначку (D51).
Assistant шле звіти лише після `assistant/registered` на поточному з'єднанні
(до нього оркестратор не знає, чий це Assistant); звіти незавершених запусків і
останнього завершеного після нового входу шле ще раз (N2).

- кожна подія від агента оновлює `last_event_at` — так помічаємо втрату
  звʼязку (D51);
- після відновлення звʼязку агент **досилає** накопичені логи й результат (D51);
- значення облікових даних їдуть лише в `EXECUTION_ASSIGN` по `wss` і в логи
  потрапляють як `***` (D20).

**Фаза 4 (E5):** `assign.credentials` — `{ "<credential id>": { "username", "password" } }`,
лише ті облікові дані, на які посилається `definition` (`{"credential": id, "part"}`
у входах кроків). Яких немає в організації — запуск `BLOCKED` («credentials
missing»), до Assistant нічого не йде. Assistant підставляє значення в момент
кроку й замінює кожне отримане значення на `***` у **кожному** рядку логу й у
`error`; налагоджувальний лог WS пише повідомлення через `redacted()` (паролі й
токени — `***`).

### Studio-back ↔ оркестратор: перевірка сценарію (фаза 4, E3)

Запит-відповідь через брокер `orchestrator.scenario_check`
(`src/contracts`, однаково в обох репо): `{ credential_ids, providers }` →
`{ missing_credentials, providers_without_assistant, newest_assistant_version,
assistants }`. Немає облікових даних — помилка перевірки (блокує «Зберегти»);
провайдера немає в жодного Assistant чи Assistant старіші за
`min_assistant_version` — попередження. Оркестратор не відповів вчасно —
`unchecked: ["credentials", "assistants"]` (D68), «Зберегти» не блокується.

## Ухвалено (D26 ✅, D27 ✅)

**Логи** їдуть пачками, але повідомлення рівня `ERROR` надсилається негайно.
Юзеру важливо миттєво побачити, коли зламалось, а не кожен успішний крок.

**Прогрес** отримує лише той, хто підписався на конкретний `execution_id`.
Інакше при тридцяти роботах кожна відкрита вкладка тоне в чужих подіях.
