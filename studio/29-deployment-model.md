# 29. Модель розгортання — розбір пропозиції

> Розбір документа [`spec/deployment-model.md`](spec/deployment-model.md)
> (Oleksii Kulinskyi, 10/7/2026). **Статус документа — пропозиція, не
> затверджено.** Тому нижче **кандидати**, а не рішення: журнал рішень не
> змінюється, доки модель не затверджено. Код перевірено 2026-10-13.

## Що пропонується — коротко

| # | Що | Суть |
|---|----|------|
| 1 | **Marketplace** — один на платформу | каталог компонентів, складених компонентів, роботів, Business Tasks, процесів / шаблонів, Connectors; клієнт встановлює їх у своє середовище |
| 2 | **Free / Trial** — спільне середовище | багато тенантів на спільних Studio, оркестраторі й інфраструктурі; кожен логічно ізольований; ліміти тарифу |
| 3 | **Paid / Enterprise** — окремий deployment на клієнта | свої Studio, оркестратор, БД, черга / кеш, конфігурація, секрети, логи; у хмарі; deployment ≠ сервер |
| 4 | **Studio + оркестратор** — одна одиниця для клієнта | технічно — кілька контейнерів; оркестратор, наприклад, — API, Scheduler, Worker |
| 5 | **Assistant** — окремо, на машинах | реєструється у своєму оркестраторі: `Assistant #27 → Customer A → PROD → Machine` |
| 6 | **Free → Paid** — зміна розгортання, не продукту | клієнт зберігає акаунт, процеси, роботи, компоненти, налаштування, дані |

## Що вже збігається з нашими рішеннями ✅

| Пропозиція | У нас |
|------------|-------|
| Studio й оркестратор — окремо, в одному середовищі | D31: окремі сервіси; між ними RabbitMQ (D67) |
| своя черга в кожному deployment | RabbitMQ у кожному середовищі; `organization_id` у конверті кожного повідомлення (D67) |
| Assistant окремо, реєструється в оркестраторі | D3a, D10 |
| Free → Paid без втрати даних | UUID-ключі й номери в межах організації (D62): при перенесенні id не конфліктують, `RBT-184` лишається `RBT-184` |
| встановлення й оновлення артефактів | версії незмінні, вміст компонентів копіюється у версію робота (D64): оновлення з Marketplace — нова версія, не тихий перезапис. Встановлений робот іде через TEST і погодження за ТЗ |
| кожен тенант бачить лише своє | D8 (усе належить організації), D56 (Visibility) — на рівні моделі |

## Де розходиться з поточним кодом

Перевірено в `Tekra-Orchester`, `Tekra-Orchester-Face`, `Tekra-Desktop`.

| # | Тема | Як зараз у коді | Що потрібно за пропозицією |
|---|------|-----------------|----------------------------|
| 1 | **Ізоляція тенантів** | центрального фільтра за організацією немає — кожен роутер передає `organization_id` вручну; у `robots` немає `organization_id`, `routers/robot.py:36-64` не перевіряє організацію; глобально унікальні `Organization.name`, `Admin.email`, `Admin.login`, `Robot.name` | спільне середовище: ручний фільтр — головний ризик витоку між клієнтами |
| 2 | **Ліцензія** | привʼязана до «підпису машини» сервера API: SHA-256 від MAC, ОС, процесора (`services/license_service.py:48`); на організацію, з `max_users` | у контейнерах у хмарі такий підпис нестабільний; ліміти Free — це тариф організації, а такої сутності немає |
| 3 | **API / Scheduler / Worker** | APScheduler — у процесі API (`main.py:49-57`), без блокування: дві копії API — задачі двічі; WS-зʼєднання — словники в памʼяті процесу (`websockets/connection_manager.py`), без обміну між процесами | Worker не дотягнеться до десктопа, підключеного до API; планувальник має бути окремим і одним |
| 4 | **Assistant ↔ «свій» оркестратор** | адресу сервера й **назву** організації юзер вводить руками у вікні входу; ідентифікатора машини немає зовсім (D9 — лише в документації) | при Free → Paid кожен Assistant доведеться переналаштувати |
| 5 | **Адреса API у Face** | вшивається **при збірці** (`scripts/generate-api-base-url.mjs`, Vercel) | окремий deployment на клієнта = окрема збірка Face на клієнта |
| 6 | **Секрети** | ключа шифрування для облікових даних роботів (D20) немає; у відкритому вигляді — `admins.two_factor_secret`, `refresh_token`, `password_reset_token`, `licenses.password` | «Secrets / Credentials» у кожному deployment; при Free → Paid — перешифрування |
| 7 | **Акаунти** | реєстрація адміна (і через Google) завжди створює нову організацію; адмін — рівно в одній організації | для самореєстрації у Free підходить; але «зберігає акаунт» при переході — це переїзд акаунта в інший deployment з іншою адресою |

## Кандидати в рішення

Не прийняті — чекають затвердження моделі. Розділені на ті, що варто закласти
одразу (вони правильні за будь-якої моделі розгортання), і ті, що залежать від
відповідей автора.

### Варто закласти у фазі 0 за будь-якої моделі

| Кандидат | Що | Чому за будь-якої моделі |
|----------|----|--------------------------|
| **К1. Ізоляція тенантів** | обовʼязковий фільтр за організацією в базовому репозиторії + **Row-Level Security** у Postgres як другий рубіж — база не віддасть чужі рядки, навіть якщо фільтр забули | у нас уже багато організацій на одному оркестраторі; витік між ними — дірка й сьогодні (п. 1) |
| **К2. Планувальник окремо, команди десктопам — через спільний канал** | планувальник — окремий процес в одному екземплярі; команди до WS-зʼєднань — через RabbitMQ (D67), щоб будь-який процес міг достукатись до десктопа | без цього оркестратор не масштабується взагалі; у [10-roadmap](10-roadmap.md) це стояло як «не блокує MVP» |
| **К3. Адреса API для Face — під час запуску** | `config.json`, що читається при старті, замість вшитої при збірці | одна збірка Face на всі середовища — і для dev / stage сьогодні |
| **К4. Підключення Assistant за токеном** | адмін у Face генерує токен або файл підключення з адресою оркестратора й організацією; Assistant реєструється раз, отримує `machine_key` (D9) | прибирає ручне введення адреси й назви організації; переїзд = новий токен |
| **К5. Ключ шифрування секретів на deployment** | облікові дані роботів (D20) шифруються ключем середовища | D20 однаково цього вимагає |

### Залежать від відповідей автора

| Кандидат | Що |
|----------|----|
| **К6. Тариф і ліміти організації** | запуски, одночасні запуски, сховище, кількість Assistant, функції; перевірка — у місцях на кшталт перевірки №17 перед запуском і реєстрації машини |
| **К7. Ліцензія на deployment** | замість привʼязки до «заліза» сервера |
| **К8. Перенесення Free → Paid** | експорт тенанта з **обох** БД (Studio й оркестратора), аудит, перешифрування секретів, переналаштування Assistant |
| **К9. Marketplace** | фактично **третій сервіс**: формат пакета (JSON-DSL, D1), походження артефакта, встановлення як DRAFT, підпис пакета, облікові дані не пакуються — привʼязуються при встановленні |

## Питання до автора

1. **Business Tasks і Connectors** — чого немає ні в ТЗ, ні в нас. Business Task
   — те саме, що Task у BPMN (ТЗ §3.2), чи окрема сутність? Connector — рівень API
   з §3.2 чи щось інше?
2. **Marketplace:** хто публікує — лише TEKRA чи й клієнти? Чи бувають платні
   артефакти? Чи має Enterprise-deployment доступ до Marketplace, якщо він
   закритий від інтернету?
3. **Хто обслуговує deployment:** лише TEKRA у хмарі чи клієнт може поставити у
   себе? Від цього залежать оновлення, ліцензування й доступ до Marketplace.
4. **Assistant #27:** чи має Assistant свій номер, окремо від машини? Чи може на
   одній машині (Windows Server) працювати кілька Assistant? «→ PROD» — це
   привʼязка Assistant до контексту? ТЗ §4.8: «один Assistant для TEST і PROD»;
   у нас — призначення машини PROD / TEST / ANY (D70).
5. **Free → Paid:** які дані переносяться (історія запусків, аудит)? Що з
   тенантом у спільному середовищі після переходу? Чи можливий зворотний перехід?
6. **Акаунт:** глобальний акаунт платформи (Marketplace, оплата) чи лише акаунт
   усередині deployment?
7. **Версії:** усі deployment на одній версії платформи чи кожен клієнт
   оновлюється окремо?
