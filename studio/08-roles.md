# 8. Ролі та доступ

## Що вже є в коді (перевірено 2026-08-20)

Сходинка ролей **уже оголошена** і спільна для таблиць `admins` і `users`:

```python
class Role(str, Enum):
    ADMIN = "ADMIN"
    DEVELOPER = "DEVELOPER"
    USER = "USER"
```

- запросити юзера можна як `USER` або `DEVELOPER` — підвищення до `ADMIN`
  через API заборонено (`_USER_ROLE_ALLOWED` у `schemas/user.py`);
- у Face уже є інтерфейс призначення ролі: діалог редагування юзера містить
  пункт `Developer — Hands-on actions`.

**Але:** пошук по `routers/` і `services/` не знаходить **жодної перевірки
ролі**. Роль зберігається, фільтрується у списках, показується в UI — і ні на
що не впливає. Прав вона поки не дає й не забирає.

Тобто сходинка є, але без зубів. Studio — природний привід їх додати.

## Розподіл ролей у Studio (D23 ✅ варіант B)

| Роль | Де працює | Що робить у Studio |
|------|-----------|--------------------|
| `USER` | десктоп + веб (обмежено) | запускає роботів, бачить свої запуски й логи. Роботів не редагує |
| `DEVELOPER` | веб + десктоп | **основна роль Studio**: створює й редагує роботів, захоплює елементи, публікує версії |
| `ADMIN` | веб | усе вищеперелічене + керування організацією, юзерами, ліцензіями, машинами |

Головна думка: робота будує той, **хто знає процес**. Тому `DEVELOPER` — це не
програміст, а досвідчений співробітник відділу.

## Що це тягне за собою

1. **Юзерський вхід у веб.** Зараз Face ходить тільки в `/admins/login`,
   `/admins/me`, `/admins/ws`. Юзери у веб потрапити не можуть узагалі.
2. **Навігація за роллю.** `USER` не має бачити ліцензії, адмінів,
   налаштування організації.
3. **Перевірки прав на бекенді.** Зараз їх немає. Ховати пункти меню
   недостатньо — доступ має різатись на рівні API.
4. **Права на роботів.** Робот належить організації (D8). Треба вирішити, чи
   будь-який `DEVELOPER` редагує будь-якого робота організації.

## Ухвалено (D24 ✅, D25 ✅)

**Вхід** — одна форма для всіх, бекенд визначає, хто зайшов. Обовʼязкова умова:
один логін не може існувати одночасно в `admins` і в `users`.

**Матриця прав** — затверджена, повна таблиця в
[02-decisions.md](02-decisions.md) → D25. Коротко:

- `DEVELOPER` може редагувати **будь-якого** робота організації і бачити чужі
  логи — інакше звільнення автора залишає робота без підтримки;
- остаточне видалення робота — тільки `ADMIN`, бо воно знищує історію запусків;
- `USER` бачить і запускає **лише дозволених йому** роботів.

Останній пункт вимагає нової звʼязки «робот ↔ юзер» у моделі даних.
