# 17. Чи дозволено виконання: Authorization, Test Period, Approvals

> Під ТЗ §4.1.7, §4.1.12–15, §4.7.2. Рішення D36–D38 — ✅ прийнято 2026-09-17. Таблиці — у [03-data-model.md](03-data-model.md), кроки 8 і 9.

## Три речі, одне питання

Усі три відповідають на одне питання — **«чи можна зараз запустити цього
робота?»** — але з різних боків:

| Що | На що відповідає | Де живе |
|----|------------------|---------|
| **Authorization** | чи погоджена ця версія для PROD | на версії |
| **Test Period** | чи можна зараз тестувати цього робота | окремий запис на робота |
| **Approval** | хто, коли й навіщо попросив дозвіл — і що вирішив адмін | черга погоджень |

Коротко: **Authorization і Test Period — це стан** («можна / не можна»).
**Approval — це запит і рішення**, які цей стан змінюють.

Аналогія:

- **Authorization** — чи є в тебе постійна перепустка;
- **Test Period** — тимчасова перепустка на день;
- **Approval** — заява на перепустку й підпис начальника на ній.

## Authorization: де зберігати (D36 ✅)

### Проблема

ТЗ кладе Authorization і на робота (§4.1), і на версію (§4.1.5). А ключове
правило каже: погодження привʼязане **до конкретної версії**, і з v27 на v28 не
переноситься (§4.1.7).

| | Варіант | Проблема |
|---|---------|----------|
| A | зберігати в обох таблицях | два джерела правди — рано чи пізно розійдуться |
| B | зберігати **тільки на версії**; у робота — обчислювати | потрібне чітке правило обчислення |
| C | зберігати тільки на роботі | порушує ключове правило ТЗ §4.1.7 |

### Рішення — B

У базі поле живе лише в `robot_versions`. Authorization робота API й Studio
**показують**, але рахують так:

```
Authorization робота =
   є Active Production Version?     → authorization цієї версії
   ні, але є версія на погодженні?  → PENDING_APPROVAL
   ні, але останній запит відхилено? → REJECTED
   інакше                            → не показується: на PROD ще не подавали
```

### Перевірка на прикладах із самого ТЗ

| Ситуація з ТЗ | Що дає правило | Збіг |
|---------------|----------------|------|
| §4.1.6 — Lifecycle PROD, Authorization PENDING_APPROVAL | активної версії ще немає, v12 на погодженні → PENDING_APPROVAL | ✅ |
| §5, кроки 9–10 — погоджено, Active PROD = v12 | активна v12 погоджена → APPROVED | ✅ |
| §5, крок 12 — створено v13, погодження v12 не переноситься | робот APPROVED (працює v12); у v13 свій окремий стан | ✅ |
| v27 активна, v28 подали на погодження | робот APPROVED — працює v27; v28 PENDING окремо | ✅ |
| адмін відкликав v27 | активна v27 REVOKED → робот REVOKED, PROD-запуски блокуються перевіркою №6 (§4.7.2) | ✅ |

## TEST — тільки через Test Period (D37 ✅)

### Питання

Відкрите питання ТЗ **#25**: чи має TEST-версія окремий authorization object,
чи дозвіл на тест дає тільки Test Period?

### Рішення — тільки Test Period

Аргумент — із самого ТЗ. §4.1.13: під одним Test Period розробник створює v10,
v11, v12 і запускає робота 800 разів **без нових погоджень**.

Якби кожна тестова версія мала власну авторизацію, кожна нова версія вимагала б
нового погодження — прямо протилежне тому, що написано в ТЗ.

Отже:

- `robot_versions.authorization` стосується **лише PROD**;
- у TEST дозвіл дає **Test Period робота** — один на всі його версії.

Попутно це підтверджує підказку до питання **#26**: період охоплює й версії,
створені вже після його видачі (у ТЗ §7 Test Period привʼязаний до `RobotID`, а
не до версії).

## Як працює Test Period

Потрібен **лише** якщо в організації увімкнено `TEST Approval Required`
(§4.1.12). Вимкнено — тестувати можна без періоду.

```
 Developer ──«Дай тестовий період на 1 день»──► запит на погодження
                                                        │
                                                      Admin
                                                 ┌──────┴──────┐
                                              APPROVE        REJECT
                                                 │              │
                                    період видано           відхилено
                                    valid_from … valid_to
                                                 │
            всередині періоду: будь-які версії, скільки завгодно запусків, без погоджень
                                                 │
                                   настав valid_to ──► EXPIRED
                                                 │
                           нові TEST-запуски ──► BLOCKED
                           уже запущені ──────► за політикою організації:
                                                ALLOW_TO_FINISH або TERMINATE
```

Адмін також може видати період сам, без запиту (§6 «Admin надає»), і відкликати
його достроково (§4.1.14).

### Статуси періоду

ТЗ називає поле Status, але значень не дає. Прийнято в складі D37:

| Статус | Що означає |
|--------|------------|
| `REQUESTED` | попросили, чекає рішення адміна |
| `APPROVED` | видано. **Діє**, коли поточний час між `valid_from` і `valid_to` |
| `REJECTED` | відхилено |
| `REVOKED` | адмін відкликав достроково |
| `EXPIRED` | час вийшов |

### Коли саме блокується запуск

Блокування спрацьовує **одразу о `valid_to`**: перевірка №9 (§4.7.2) дивиться на
час, а не на статус.

Статус `EXPIRED` і запис в аудит («expire», §4.7.5) ставить періодична задача
APScheduler. Якщо вона запізниться на хвилину — запуск однаково не пройде.

### Одне обмеження

У робота одночасно може бути **лише один чинний** період. Два періоди, що
перекриваються, дали б незрозуміло, за яким із них діє політика закінчення.

## Move to PROD (§4.1.15)

```
 Developer обирає версію ──► «Move to PROD»
                                 │
                        lifecycle робота = PROD
                                 │
                   PROD Approval Required увімкнено?
                  ┌──────────────┴──────────────┐
                 ні                              так
                  │                               │
   authorization версії = NOT_REQUIRED     authorization версії = PENDING_APPROVAL
   Active Production Version = ця версія   запит на погодження PROD_PROMOTION
                                                  │
                                                Admin
                                          ┌───────┴───────┐
                                       APPROVE          REJECT
                                          │                │
                            authorization = APPROVED   authorization = REJECTED
                            Active Production Version   активна версія
                              = ця версія                не змінюється
```

`lifecycle = PROD` ставиться вже в момент «Move to PROD», ще до погодження — так
у ТЗ §4.1.15 (крок 7) і §5 (крок 8). Тому можливий стан «PROD, але ще не
погоджено», і запуск у ньому заборонений (§4.1.6).

**Що свідомо не вирішуємо в цьому блоці:** як при цьому змінюється Release State
версії (RELEASED, SUPERSEDED) і хто вважається «тим, хто виконав release». ТЗ
окремо розділяє «хто виконав release» і «хто виконав approval» (§4.1.2), але
модель Release State лишив відкритою (**#23**). Це наступний крок.

## Approvals: одна черга на базі наявного скелета (D38 ✅)

### Що вже є в коді

| Де | Що |
|----|----|
| Orchester | таблиця `approvals`, `GET /approvals/pending`, `POST /approvals/bulk-approve` |
| Face | картка «Deployments pending approval» у дзвіночку, сторінка Approvals |

### Чого бракує, щоб це працювало за ТЗ

| Бракує | Чому важливо |
|--------|--------------|
| **посилання на обʼєкт** | зараз у запиті лише текстова мітка `entity_label`. Погодження **нічого в системі не змінює** |
| хто попросив | ТЗ §4.1.2: окремо фіксувати, хто створив версію, хто зробив release, хто погодив |
| причина рішення | подія аудиту вимагає Reason (§4.7.5) |
| відхилення | є лише масове погодження — відхилити нічим |
| тип для Test Period | зараз єдиний тип `DEPLOYMENT` |

### Рішення

Одна черга для обох видів погоджень:

| Тип | Що погоджують | Що змінює рішення |
|-----|---------------|-------------------|
| `PROD_PROMOTION` (було `DEPLOYMENT`) | версію для PROD | `robot_versions.authorization`, `robots.active_production_version_id` |
| `TEST_PERIOD` | тестовий період | `test_periods.status` |

**Правило:** стан живе на обʼєкті (версія, період). Approval — це запит і
рішення, тобто історія.

**Відкликання (REVOKE)** — не рішення по запиту, а окрема дія адміна над уже
погодженим обʼєктом. Воно змінює стан обʼєкта й пишеться в аудит. Рядок
погодження лишається `APPROVED`: історію не переписуємо.

**`CANCELLED`** — наше доповнення до статусів запиту: розробник відкликав свій
запит або робота заархівували, поки запит чекав.

### Що це зачепить у коді (не зараз)

- Face: `ApprovalType = 'DEPLOYMENT'` у `types/approval.types.ts`;
- підпис картки в дзвіночку «Deployments pending approval».

## Налаштування, від яких усе це залежить

Усе вище вмикається політиками організації з Admin Panel (§4.7.4):

- `TEST Approval Required` ON / OFF;
- дозволені тривалості Test Period і максимальна тривалість;
- поведінка після закінчення періоду: `ALLOW_TO_FINISH` / `TERMINATE`;
- `PROD Approval Required` ON / OFF.

Де й як їх зберігати — окремий блок «Політики». Аудит змін політик ТЗ теж
вимагає (§4.7.5), тож прості прапорці в `organizations` можуть не підійти.
