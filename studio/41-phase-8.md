# 41. Фаза 8 — компоненти, процеси, налагодження: задачі

> Що: розширення поверх робочого редактора — компоненти з копіюванням у версію
> робота (D58, D64), BPMN-процеси як модель (D57, D78), налагодження частин версії
> (D66). Проєктування — [25-bpmn-components.md](25-bpmn-components.md),
> [27-partial-runs.md](27-partial-runs.md).

## Етапи

Фаза завбільшки з фазу 6 — три етапи, кожен із живим прогоном:

| Етап | Що | Чому в такому порядку |
|------|----|-----------------------|
| **8A** | Custom components: картка й версії в Studio-back, редактор компонента, крок «компонент» у роботі, копія вмісту у версію (D64), виконання в Assistant з власною областю змінних | дає повторне використання — найбільша цінність для розробника |
| **8B** | BPMN-процеси: картка й версії, Business Tasks (D78), редактор (bpmn-js — спершу ліцензія), задача → робот, здоров'я процесу | модель; нічого не виконує — не заважає решті |
| **8C** | Налагодження: точки зупинки / «до цього кроку» і «Запустити виділене» (`executions.scope`), пауза, крок, змінні живою подією | зачіпає протокол і виконавця — окремо від компонентів, щоб не змішувати |

## Етап 8A — рішення

| # | Питання | Рішення | Чому |
|---|---------|---------|------|
| 1 | Де живуть компоненти | лише в Studio-back: `components` (картка, номер `CMP-n` з лічильника організації, робоча копія, архів) і `component_versions` (`(component_id, number)`, `definition`, хеш, опис змін, автор). Оркестратору компоненти не потрібні — вміст іде у версію робота (D64) | D31, D64, 28 |
| 2 | Що таке `definition` компонента | `{ parameters, steps, elements, result }`: параметри — як у робота (D22), кроки й елементи — свої (D58), `result` — ім'я змінної, значення якої повертається; без тригерів і без інших компонентів | D58: компонент не містить інших компонентів |
| 3 | Крок «компонент» у роботі | `activity = "flow/Component"`, `component: { id, number, version, name }` — у робочій копії лише посилання; `inputs` — значення параметрів (можна `{{змінна}}`), `output` — куди покласти результат | у каталозі — блок керування; провайдер `flow` уже знає кожен Assistant, старі відсікає `min_assistant_version` |
| 4 | Копія у версію (D64) | при «Save» Studio-back розгортає кожен крок-компонент: `component.definition` = вміст вказаної версії компонента. Хеш версії робота — від розгорнутого `definition`; «нічого не змінилось» (D34) — теж | D64: версія самодостатня, Assistant нічого не дотягує |
| 5 | Перевірки | компонент і версія існують і належать організації; `inputs` — лише параметри компонента, обов'язкові задані (значення або шаблон); заархівований компонент новим роботам не пропонується, але наявні посилання працюють; розгорнутий `definition` перевіряє й оркестратор (контракт) | 14-validation |
| 6 | Виконання (Assistant) | крок-компонент виконує вкладені кроки з **власною областю змінних**: усередину — лише параметри (з `default`), назовні — лише `result` у `output`; елементи — компонента; кроки в логах — `s1/s3`; помилка всередині — помилка кроку `s1` (TryCatch навколо працює) | 25-bpmn-components, «Як виконується» |
| 7 | Провайдери й облікові дані | перевірка №12 рахує провайдери й усередині компонентів; облікові дані (D20, D69) — за всім `definition`, тож і в компоненті | інакше компонент обійшов би перевірки |
| 8 | Нова версія компонента | робот сам не змінюється (D58): у редакторі робота — «є новіша версія 7.4 → оновити», що змінює робочу копію → нова версія робота | D58, D64 |
| 9 | Аудит | Studio-back шле `studio.component_version.created`, `studio.component.archived` → оркестратор пише `COMPONENT_VERSION_CREATED`, `COMPONENT_ARCHIVED` (28: «лише аудит») | 19-audit, 28 |
| 10 | UI Studio-front | сторінка Components (список, створити, архів), редактор компонента (той самий редактор кроків, параметри, `result`, бібліотека елементів), у редакторі робота — компоненти в палітрі, форма кроку з параметрів компонента, підказка про новішу версію | D82 |
| 11 | Окремий запуск компонента | ні (D66): компонент тестують у роботі — кроком, а з 8C — «Запустити виділене» | D66 |

Як зроблено:

- **Контракт** — `ComponentDefinition`, `ComponentRef`, `Step.component`, константа
  `COMPONENT_ACTIVITY = "flow/Component"`; спільна перевірка дерева (`_check_tree`) для
  робота й компонента; `RobotDefinition.component_steps()`; події
  `ComponentVersionCreated`, `ComponentArchived`. Каталог: `flow/Component`
  (min 1.4.0, `catalog_version` 2).
- **Studio-back** — `components`, `component_versions`, `organization_counters.next_component_number`
  (міграція `a7c3e5f1d208`); `ComponentService` (картка, робоча копія, перевірка, версії,
  архів, `expand` — копія вмісту в кроки робота); `RobotVersionService` розгортає
  компоненти і перед перевіркою, і при «Save»; валідатор перевіряє параметри кроку-компонента
  й рахує активності, провайдери й облікові дані всередині.
- **Оркестратор** — `providers()` заходить у компоненти; аудит подій компонента
  (міграція `c2f6a9d4e817`).
- **Assistant 1.4.0** — `flow/Component`: параметри в області виклику, вкладені кроки з
  власною областю й елементами, `result` → `output`, шляхи `s1/c1` у логах, помилка
  всередині — помилка кроку виклику.

| # | Питання | Рішення | Чому |

Ліцензія bpmn.io: безкоштовно, зокрема для комерційного закритого продукту; **водяний знак bpmn.io не прибирається й не перекривається** — ми його не чіпаємо | ліцензію перевірено 2026-11-08 (bpmn.io/license, LICENSE у репо) |
| 2 | Де живуть процеси | лише Studio-back: `processes` (картка, `PRC-n` з лічильника, робоча копія — BPMN XML, архів), `process_versions` (`(process_id, number)`, XML, хеш, опис змін, автор), `business_tasks` (ідентичність задачі: номер `BT-n` в організації, процес, id елемента BPMN, архів), `process_version_tasks` (вміст задачі у версії: назва, опис, тип виконавця, робот, доріжка) | D57, D78: ідентичність окремо, вміст — у версії |
| 3 | Тип виконавця й робот | атрибути елемента BPMN у власному просторі імен: `tekra:executor` = `HUMAN` / `AI` / `SYSTEM` / `ROBOT`, `tekra:robotId` (для ROBOT). bpmn-js зберігає чужі атрибути при експорті | D78; XML лишається стандартним BPMN 2.0 |
| 4 | Що дозволено в схемі | один `process`: Start / End Event, задачі (`task`, `userTask`, `serviceTask`, `manualTask`), Exclusive Gateway, Sequence Flow, Lane; інше — помилка; потрібні хоч одна Start і одна End; `ROBOT` без робота чи з чужим роботом — помилка. `<!DOCTYPE>` відкидається (захист парсера) | D57: набір MVP |
| 5 | Ідентичність задачі | `business_tasks` — за парою (процес, id елемента BPMN): елемент, що лишився в новій версії, — та сама задача; новий — нова `BT-n`; зниклий — задача лишається в історії | D78 |
| 6 | Версії | як у роботів (D34): нова — лише коли XML змінився (хеш); без TEST / PROD і погоджень | D57 |
| 7 | Здоров'я процесу | найгірше з Health роботів його задач (ERROR / OFFLINE > WARNING > HEALTHY; робот без Health не рахується); рахує Studio-front з `GET /robots` оркестратора — кожне зі свого сервісу | D57, D31 |
| 8 | Аудит | `studio.process_version.created` → оркестратор пише `PROCESS_VERSION_CREATED` (28: «лише аудит») | 19-audit |
| 9 | UI | Processes: список (PRC-n, назва, версія, здоров'я); редактор: полотно bpmn-js + бічна панель вибраної задачі (назва, опис, виконавець, робот зі списку), перевірка, «Save version», версії | D82 |
