# 5. Селектори

> ⚠️ **Сира перша версія.** Читати після [04-approach.md](04-approach.md):
> формат селектора залежить від обраного провайдера.
> Це найризикованіша частина всієї системи, і в
> реальних програмах вона майже напевно зміниться. Мета зараз — домовитись про
> напрямок, а не зафіксувати фінальний формат.

## Що таке селектор

Опис, **як знайти елемент на екрані**. Коли робот має натиснути кнопку
«Провести», він мусить її спершу знайти — у вікні, яке щоразу трохи інше.

Це найчастіша причина, чому RPA-роботи ламаються в проді. Не логіка, не мережа
— саме «не знайшов кнопку».

## Чому селектори ламаються

| Що сталось | Приклад |
|------------|---------|
| Змінилась назва | оновили програму, кнопка стала «Провести і закрити» |
| Заголовок вікна динамічний | «Документ №123 — 1С», а завтра №124 |
| Елемент без сталого ідентифікатора | старі програми часто не дають нічого, крім позиції |
| Змінився масштаб чи роздільна здатність | координати поїхали |
| Елемент зсунувся у списку | рядок був третій, став пʼятий |
| Інша мова інтерфейсу | «Save» замість «Зберегти» |

Висновок: **прив'язуватись до чогось одного не можна.**

## Що взагалі можна побачити у вікні Windows

Windows має службу **UI Automation (UIA)** — вона показує вміст вікна як дерево
елементів. У кожного елемента є властивості:

| Властивість | Приклад | Наскільки стабільна |
|-------------|---------|---------------------|
| `AutomationId` | `btnPost` | 🟢 найкраща, якщо програма її задає |
| `ControlType` | `Button`, `Edit`, `Tree` | 🟢 стабільна, але не унікальна |
| `ClassName` | `WindowsForms10.BUTTON` | 🟡 стабільна, часто не унікальна |
| `Name` | «Провести» | 🟡 ламається при оновленні та зміні мови |
| Позиція | x=340, y=210 | 🔴 ламається від усього |

Тим самим механізмом користуються всі великі RPA-платформи. Ми не винаходимо
велосипед — ми вирішуємо, **що саме з цього записувати**.

## Пропозиція формату

### Ідея 1: селектор — це ланцюг, а не одна ознака

Елемент описується шляхом від вікна вниз:

```
вікно «1С:Підприємство*»
   └── панель mainPanel
         └── кнопка btnPost
```

Так само працюють UiPath і Power Automate Desktop. Ланцюг дає контекст: кнопок
«Провести» у програмі може бути пʼять, але в цій панелі — одна.

`*` — підстановка: «заголовок починається з». Це рятує від динамічних
заголовків на кшталт «Документ №123».

### Ідея 2: селектор — це **список способів**, а не один спосіб

Головна думка. Замість одного опису зберігаємо кілька, впорядкованих за
надійністю. Executor пробує по черзі, поки не знайде.

```
1. за AutomationId          ← найточніше
2. за назвою + типом        ← якщо id немає
3. відносно сусіда          ← «поле праворуч від напису Сума»
4. за картинкою             ← крайній випадок
```

Це те, що відрізняє робота, який живе рік, від робота, який ламається після
першого оновлення програми.

**Важливий побічний ефект:** якщо елемент знайдено не першим способом, це треба
записати в лог. Тоді юзер бачить «знайшов резервним способом» — сигнал, що
селектор варто перезахопити **до** того, як робот остаточно зламається.

### Приблизний вигляд у JSON

```json
{
  "strategies": [
    {
      "kind": "uia",
      "path": [
        { "control": "Window", "name": "1С:Підприємство*" },
        { "control": "Pane",   "id": "mainPanel" },
        { "control": "Button", "id": "btnPost" }
      ]
    },
    {
      "kind": "anchor",
      "anchor":   { "control": "Text", "name": "Сума" },
      "relation": "right_of",
      "target":   { "control": "Edit" }
    }
  ]
}
```

Формат — **завжди список**, навіть якщо спосіб один. Тоді додати резервні
варіанти пізніше можна без міграції сценаріїв.

## Пропозиція: знімок захоплення окремо від активного селектора

> Статус: ✅ ухвалено (D7a).

Коли юзер тицяє на елемент, Inspector бачить **набагато більше**, ніж потрапить
у селектор: усі властивості самого елемента і всіх його предків, сусідів,
підписи поруч.

Пропозиція — зберігати це повністю, окремо від активного селектора:

| Що | Роль |
|----|------|
| **Знімок захоплення** | сирі дані, як усе виглядало в момент кліку. Не використовується при виконанні |
| **Активний селектор** | те, чим Executor реально шукає елемент. Генерується зі знімка |

Що це дає:

- селектор зламався — можна **перегенерувати з знімка**, не бігаючи до юзера з
  проханням перезахопити;
- Studio може показати «раніше кнопка звалась *Провести*, тепер *Провести і
  закрити*» — юзер бачить причину, а не просто «не знайшов»;
- можна змінити алгоритм побудови селекторів і **переграти його на старих
  захопленнях**, не чіпаючи роботів.

Ціна — кілька кілобайт JSON на елемент. Оскільки сценарій і так лежить у
`JSONB` (D4), це фактично безкоштовно.

## Це формат саме для UIA-провайдера

Описане вище стосується провайдера `desktop-uia`. У браузера буде свій формат —
див. [04-approach.md](04-approach.md).

## Ухвалено (D7a ✅, D7b ✅)

**Шлях із пропусками рівнів.** Обовʼязкові лише вікно і сам елемент; проміжні
вузли — підказки. Вставили панель в оновленні — селектор вижив.

```
Window «1С:Підприємство*»
   ⋮   (скільки завгодно рівнів)
   Button  id=btnPost
```

**Знімок захоплення зберігається окремо** від активного селектора.

**Пошук по картинці** в MVP не входить (провайдер `image` не увійшов у D17),
але місце у форматі під нього лишається.
