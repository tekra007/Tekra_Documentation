# Studio окремим сервісом — простими словами

## Про що питання

Зараз Studio і оркестратор — **одна програма**. Ідея: зробити дві окремі, які листуються через «пошту» (FastStream).

*Аналогія: зараз усі сидять в одній кімнаті й гукають через стіл. Пропозиція — розселити по двох будівлях і листуватись.*

Плюс: ремонт в одній будівлі не заважає іншій.
Мінус: усе, що було «гукнув через стіл», стає листом.

---

## Хто з ким говорить **зараз**

```
   Браузер (Face)                        Десктоп (агент)
        │                                       │
   HTTP │  /admins/login, /users,          WS   │  /users/ws
        │  /licenses, /logs, /robots/...        │  логін, список роботів,
    WS  │  /admins/ws                           │  start / pause / stop,
        │  сповіщення адмінам                   │  розклад
        │                                       │
        └────────────► Оркестратор ◄────────────┘
                            │
                     Postgres · Redis
```

Три важливі речі:

1. **Браузер і десктоп ніколи не бачать одне одного** — усе через оркестратор
2. **У десктопа рівно одне зʼєднання** — через нього ходить усе
3. Адмін тисне «запустити» → HTTP в оркестратор → той **проксіює** команду в десктоп по вже відкритому WebSocket

## Хто з ким говоритиме **за нашим планом**

```
   Браузер (Studio у складі Face)          Десктоп (агент)
        │                                        │
   HTTP │  /activities   каталог кроків     WS   │  /users/ws
        │  /robots       робот і версії          │
        │  /validate     перевірка               │   MACHINE_REGISTER
        │  /jobs         запуск                  │   INSPECT_START / RESULT
        │  /machines     машини                  │   JOB_ASSIGN / PROGRESS
        │  /credentials  облікові дані           │   JOB_LOG / FINISHED
        │  /schedules    розклади                │
    WS  │  /admins/ws                            │
        │  прогрес запуску, логи наживо,         │
        │  сесія Inspector, статус машин         │
        │                                        │
        └────────────► Оркестратор ◄─────────────┘
                    ┌────────────────┐
                    │  studio        │  ← «збирати роботів»
                    │  ─── двері ─── │  ← один визначений набір викликів
                    │  runtime       │  ← «запускати роботів»
                    └────────────────┘
                          Postgres
```

Каналів **два**, і обидва **вже існують**. Нових зʼєднань не додається — тільки нові повідомлення в наявні. Межа між `studio` і `runtime` зʼявляється, але вона **в коді, а не в мережі**.

## Хто з ким говорив би, **якби розділили**

```
   Браузер
      │ HTTP + WS
      ▼
   Studio (окремий сервіс)
      │
      ├── HTTP ──────► Оркестратор     «дай машини», «чи живий агент»,
      │  (треба відповідь зараз)        «чи не видалили облікові дані»
      │
      └── брокер ────► Оркестратор     «версію опубліковано»,
         (FastStream)                   «запусти робота»
                            │
                            │ WS
                            ▼
                        Десктоп
      │
      ▼
   Postgres  ◄── сюди ж ходить і оркестратор
```

Каналів стає **чотири** замість двох.

## Три причини не робити зараз

**1. У вас ще й одна програма не вміє працювати у двох копіях.**

Список «хто онлайн» і всі зʼєднання з десктопами лежать **у памʼяті програми**. Запустиш другу копію — вона про них нічого не знатиме.

Отже ділити заради масштабу немає сенсу: масштабу все одно не буде.

*Це як відкривати другий офіс, коли в першому телефон не працює.*

**2. Захоплення елемента стане вдвічі довшим.**

Юзер натиснув «обери елемент» і **стоїть чекає**:

| Зараз і за планом | Якби розділили |
|---|---|
| браузер → оркестратор → десктоп | браузер → Studio → брокер → оркестратор → десктоп |
| **2 переходи** | **4 переходи**, один — черга повідомлень |

І назад те саме. Кожен перехід — затримка й ще одне місце, де може обірватись.

Пошта добра для «повідом, коли закінчиш». Погана — коли людина дивиться в екран.

**3. Studio однаково весь час питатиме оркестратор.**

Перед публікацією перевіряємо: чи є машина, яка це вміє? чи не застарий агент? чи не видалили пароль? Це питання «відповідай прямо зараз».

Поштою так не роблять — довелося б додати **ще й** прямий канал. Тобто два способи спілкування замість одного.

## Що правда

Розріз між **«збирати роботів»** і **«запускати роботів»** справді існує:

| Studio | Оркестратор |
|---|---|
| роботи, версії, елементи | машини, запуски, логи |
| каталог активностей, валідація | розклади, облікові дані, звʼязок з агентами |

Це нормальний розріз. Питання лише — чи потрібні заради нього **дві програми**.

## Що робити натомість

Одна програма, але з **чіткою межею всередині**: окрема тека `src/studio/`, яка не лізе руками в чужий код, а звертається через одні двері. Події — через внутрішню шину, зроблену так, щоб її потім можна було замінити на FastStream, не переписуючи місця виклику.

*Одна будівля, але два відділи з окремими кабінетами й одним віконцем між ними. Захочеш розселити — стіна вже стоїть, лишиться винести кабінет.*

## Коли повернутись

1. зʼявиться окрема команда, яка релізить Studio окремо
2. Studio треба ставити клієнтам окремо від оркестратора
3. треба масштабувати — але **спершу** прибрати зʼєднання з памʼяті
4. деплой Studio почне ламати виконання роботів

Пункт 3 — не аргумент **за** розділення, а **умова перед ним**.
