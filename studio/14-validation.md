# 14. Валідація робота при публікації

> Чернетка. Перелік перевірок доростатиме разом з активностями.

Мета проста: **юзер має побачити зрозумілу помилку у Studio, а не незрозуміле
падіння вночі.**

## Помилки й попередження

| | Що це | Що робить |
|---|-------|-----------|
| **Помилка** | сценарій точно не спрацює | **блокує публікацію** |
| **Попередження** | сценарій спрацює, але щось підозріле | публікацію не блокує, показується |

Правило: блокуємо лише те, у чому впевнені. Надто суворий валідатор дратує й
змушує обходити систему.

## Помилки

### Структура

| Перевірка | Чому |
|-----------|------|
| сценарій порожній | нічого виконувати |
| невідома активність | немає в каталозі (D2) — Executor не знатиме, що робити |
| не заповнений обовʼязковий параметр кроку | впаде на першому ж виконанні |
| значення не того типу | «сума» замість числа отримала текст |
| `ForEach` без вкладених кроків | цикл ні про що |
| `If` без жодної гілки | те саме |

### Посилання

| Перевірка | Чому |
|-----------|------|
| крок посилається на елемент, якого немає в бібліотеці | нічого шукати на екрані |
| крок посилається на видалені облікові дані | робот не зможе увійти |
| використана змінна, яка ніде не оголошена й не є параметром | порожнє значення посеред виконання |
| змінна використана **раніше**, ніж їй присвоєно значення | типова помилка при перетягуванні кроків |

### Безпека

| Перевірка | Чому |
|-----------|------|
| у поле типу `secret` вписано константу замість посилання на облікові дані | інакше пароль осяде у сценарії та в логах — рівно те, від чого захищає D20 |

Ця перевірка — головна причина, чому тип поля `secret` узагалі зʼявився в
каталозі.

## Попередження

| Перевірка | Чому попередження, а не помилка |
|-----------|--------------------------------|
| жодна машина організації не підтримує потрібний провайдер | машину можуть додати завтра |
| версія агента на всіх машинах нижча за потрібну роботу | оновлення десктопа — питання часу |
| у селектора лише один спосіб пошуку, без резервного | працюватиме, але зламається при першому ж оновленні програми (D7a) |
| елемент захоплено дуже давно | програма могла змінитись відтоді |
| крок без назви | сценарій буде важко читати через півроку |
| оголошений параметр робота ніде не використовується | швидше за все, забули |

## Де живе валідація

**У оркестраторі.** Там каталог активностей (D2), там же публікація.

Studio не робить власну копію перевірок — інакше дві реалізації розійдуться, і
юзер бачитиме різні відповіді на одне питання. Замість цього Studio викликає
той самий валідатор окремим ендпоінтом і показує результат:

```
POST /robots/{id}/validate   →   { errors: [...], warnings: [...] }
```

Кожен запис прив'язаний до `step_id`, щоб Studio підсвітила саме той крок.

## Чого валідація при публікації **не** ловить

Вона перевіряє стан **на момент публікації**. Далі світ змінюється:

- облікові дані видалили вже після публікації;
- машину прибрали з організації;
- програма оновилась і селектор більше не знаходить елемент.

Тому:

1. видалення того, що використовується, треба **притримувати** — звідси
   `GET /credentials/{id}/usage` у [13-api.md](13-api.md);
2. решта ловиться вже під час виконання і йде у логи як помилка кроку.

Валідація зменшує кількість нічних сюрпризів, але не скасовує їх.
