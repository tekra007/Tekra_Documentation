# 25. BPMN-процеси й Custom components

> Під ТЗ §2.1, §3.2, §3.3. Рішення D57, D58 — 🟡 пропозиції пакетом, без
> окремого обговорення. Частково закриває відкрите питання ТЗ **#1**.
> Обидва блоки в MVP (D33), а ТЗ описує їх найменш детально — це **перша
> версія**, вона зміниться.

## Що каже ТЗ

- **Level 1: BPMN** — опис **бізнес-процесу** з Task-ів. Task виконує людина,
  Robot або інша роль. Task — не низькорівнева дія робота (§3.2);
- **Level 2: Robot** — складається з компонентів рівнів UI / API / Graph / OS
  (§3.2);
- **Custom components** — юзер складає власні компоненти з базових. Приклад:
  замість вузького `Login to BAS` — універсальний `Login to [selected system]`
  (§3.3).

## BPMN-процеси (D57 🟡)

### Що це в MVP — модель, а не рушій

Найважливіше рішення блоку: у MVP **процес описує, а не виконує**.

| | Модель процесу (MVP) | Рушій процесу (після MVP) |
|---|---|---|
| Що робить | показує, з яких кроків складається бізнес-процес і де в ньому роботи | сам запускає роботів по черзі, чекає людей, розгалужується |
| Приклад | «Обробка рахунків: бухгалтер отримує → робот вносить у 1С → керівник погоджує» | те саме, але система сама викликає робота, коли бухгалтер закінчив |
| Ціна | редактор + звʼязок задач із роботами | повноцінний workflow engine, інбокс задач для людей |

**Чому так:** ТЗ каже, що BPMN використовується «для **опису** бізнес-процесу», і
не вимагає виконання процесу. А рушій процесів — продукт завбільшки з усе, що ми
вже спроєктували.

### Навіщо модель без рушія

- **видно, де в бізнесі стоять роботи** — не список з 40 роботів, а процес;
- **моніторинг процесу**: здоровʼя процесу = найгірше здоровʼя його роботів
  (D52). Процес «Обробка рахунків» червоний, бо робот «Внесення в 1С» упав;
- саме це й мав на увазі розділ «Processes» у Face — він повертається (D60).

### Які елементи BPMN підтримуємо

| Елемент | Навіщо |
|---------|--------|
| Start / End Event | початок і кінець процесу |
| **User Task** | задача людини |
| **Robot Task** (Service Task) | задача робота — привʼязана до конкретного робота |
| Manual Task | задача «іншої ролі» з ТЗ |
| Exclusive Gateway | розгалуження «якщо — інакше» |
| Sequence Flow | стрілки між елементами |
| Lane | доріжка: хто виконує — відділ чи роль |

Решта BPMN 2.0 (таймери, повідомлення, підпроцеси) — не в MVP.

### Як зберігаємо

- **BPMN 2.0 XML** — стандартний формат. Процес можна відкрити в інших
  інструментах, а редактор не треба писати з нуля;
- для редактора в Angular природний кандидат — **bpmn-js** (bpmn.io).
  **Перевірити ліцензію** до вибору: вона вимагає лишати логотип bpmn.io видимим;
- звʼязок «задача → робот» додатково кладемо в окрему таблицю, щоб не розбирати
  XML при кожному запиті.

### Версії

Той самий принцип, що в роботів (D34): **робоча копія + незмінні версії**, нова
версія лише якщо схема змінилась.

Але **без TEST / PROD і без погоджень**: процес у MVP нічого не виконує, тож
погоджувати нема чого. Погоджується робот, якого процес показує.

Robot Task посилається на **робота**, а не на версію: процес показує, що робить
робот зараз, тобто його Active Production Version.

### Чого свідомо немає в MVP

- виконання процесу, інбокс задач для людей;
- виклик робота з процесу — а разом із ним і винятки TEST → PROD (D46), які саме
  тут і знадобляться.

## Custom components (D58 🟡)

### Що це

**Компонент** — готовий шматок сценарію з кроків, який можна вставити в
будь-якого робота як один крок. З параметрами на вході й результатом на виході.

```
 Компонент «Login to BAS»
   параметри:  credential  (облікові дані, D20)
               base_url
   кроки:      OpenBrowser → Navigate {{base_url}} → TypeText логін → TypeText пароль → Click «Увійти»
   результат:  —

 Робот «Обробка рахунків»
   s1  Login to BAS   credential = «BAS — бухгалтер», base_url = https://bas.local
   s2  ReadRange ...
```

У Studio компонент виглядає як ще одна активність у каталозі (D2): форма
будується з його параметрів.

### Головне правило: робот посилається на **версію** компонента

ТЗ вимагає, щоб версія робота була **незмінною** (§4.1.3). Якби робот
посилався на «останню версію компонента», зміна компонента мовчки змінювала б
поведінку вже погоджених PROD-роботів — без нової версії робота й без погодження.

Тому:

- компонент має версії за тим самим принципом D34;
- крок робота посилається на **конкретну версію** компонента;
- вийшла нова версія компонента — автор робота **сам** оновлює посилання, і це
  створює нову версію робота, яка йде звичайним шляхом через TEST і погодження.

### Обмеження MVP

| Обмеження | Чому |
|-----------|------|
| компонент **не може містити інші компоненти** | прибирає цикли й ланцюжки залежностей; додамо пізніше |
| у компонента **свої елементи** (селектори) | він логіниться в конкретну систему — її кнопки належать йому |
| версію компонента, яку використовує хоч один робот, **не можна видалити** | інакше зламалась би незмінна версія робота; компонент можна лише заархівувати |

**Про «Login to [selected system]».** Справді універсальний вхід у *будь-яку*
систему неможливий: у кожної системи свої кнопки. Реалістично — компонент,
параметризований обліковими даними й адресою, для однієї системи або родини
однакових систем. Це й закриває приклад з ТЗ.

### Як виконується

Executor розгортає кроки компонента на місці його виклику, з **власною областю
змінних**: всередину — лише параметри, назовні — лише результат. У логах крок
виглядає як шлях: `s1 › login/s3`, щоб Studio підсвітила крок усередині
компонента.

## Склад `definition` версії робота (питання ТЗ #1)

Звідси остаточно видно, що входить у `definition` — а отже, що створює нову
версію (D34), а що є metadata-only:

| Входить у `definition` — зміна створює версію | Не входить — metadata-only |
|-----------------------------------------------|----------------------------|
| кроки й порядок | назва, опис |
| умови, цикли, змінні | Owner |
| оголошені параметри робота (D22) | `change_description` |
| бібліотека елементів і селектори (D21) | Lifecycle, Availability, Health |
| **посилання на версії компонентів** | доступ юзерів (`robot_access`) |
| посилання на облікові дані (за id, D20) | розклади |
| `min_assistant_version` | |

## Модель даних

Коротко — таблиці в [03-data-model.md](03-data-model.md), кроки 12 і 13.

| Таблиця | Що |
|---------|----|
| `processes` | картка процесу: `code` виду `PRC-000012`, назва, опис, власник, робоча копія, вказівник на поточну версію, архів |
| `process_versions` | незмінна версія: BPMN XML, хеш, автор, опис змін |
| `process_tasks` | задачі версії: id елемента BPMN, тип (USER / ROBOT / MANUAL), `robot_id` для задач робота, доріжка |
| `components` | картка компонента: `code` виду `CMP-000007`, назва, опис, власник, робоча копія, поточна версія, архів |
| `component_versions` | незмінна версія: параметри, результат, кроки, елементи — у JSONB; хеш; автор |

Події аудиту доповнюються: `PROCESS_VERSION_CREATED`, `COMPONENT_VERSION_CREATED`,
`COMPONENT_ARCHIVED`. У ТЗ їх немає, але компоненти прямо впливають на виконання
роботів.
