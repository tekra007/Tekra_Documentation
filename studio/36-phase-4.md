# 36. Фаза 4 — редактор Studio: задачі

> Розбивка фази 4 з [10-roadmap.md](10-roadmap.md). Складено 2026-11-08 після фази 3
> ([35](35-phase-3.md)). Рішення ухвалено того ж дня (людина доручила агенту
> вирішувати самому). Підстави — D2 (змінено в 28), D14, D20, D68,
> [14-validation.md](14-validation.md), [12-screens.md](12-screens.md).
>
> **Мета фази 4:** розробник збирає робота **без сирого JSON**: список кроків із
> вкладеністю, форма кроку з каталогу активностей, елементи з бібліотеки, облікові
> дані з випадайки. Studio перевіряє сценарій (помилки блокують «Зберегти»,
> попередження — ні) і рахує `min_assistant_version`. Облікові дані зберігаються
> зашифровано в оркестраторі, у сценарії — лише посилання, у логах — `***`.

## Рішення

| # | Питання | Рішення | Чому |
|---|---------|---------|------|
| 1 | Де й у якому вигляді каталог | **дані**, а не код: `src/catalog/activities.json` у Studio-back (D2, 28); `GET /activities`. Копія того самого файлу — у десктопі; правило як для `contracts`: файли однакові (`diff`) | одне джерело правди для форм, перевірки й `min_assistant_version` |
| 2 | Контрактний тест «реалізовано == є в каталозі» | у десктопі: кожна активність каталогу реалізована в `ExecutionRunner` і навпаки, і кожен вхід, який читає реалізація, описаний у каталозі | десктоп — єдине місце, де є і реалізація, і копія каталогу; CI окремих репо не бачить одне одного |
| 3 | Що в записі каталогу | `name`, `provider`, `title`, `description`, `min_assistant_version`, `inputs[]` (`name`, `type`, `required`, `default`, `options`, `title`, `description`), `output` (`none` / `optional` / `required`), `blocks` | рівно те, що треба формі й перевірці (14) |
| 4 | Типи входів | `text` (шаблони `{{…}}`), `text_or_secret`, `number`, `boolean`, `enum`, `element`, `variable` (ім'я), `keys`, `json` | `secret` (D20) — окремий тип, щоб пароль не вписали константою |
| 5 | Посилання на облікові дані | значення входу — `{"credential": "<id>", "part": "password" \| "username"}` | D20: у сценарії лише id |
| 6 | Де перевірка | `ScenarioValidator` у Studio-back (28): структура й типи за каталогом, посилання на елементи, змінні (оголошена до використання), безпека; оркестраторне (облікові дані існують, провайдер є хоч на одній машині, версія Assistant) — запит `orchestrator.scenario_check` через брокер; не відповів за 2 с — `unchecked` (D68) | 14, D68 |
| 7 | Що блокує «Зберегти» | помилки локальної перевірки й помилка «облікових даних немає», якщо оркестратор відповів; попередження й `unchecked` — ні | 14: блокуємо лише те, у чому впевнені |
| 8 | `min_assistant_version` | Studio-back рахує при «Зберегти» як найбільшу з активностей сценарію; Assistant звітує свою версію (`ASSISTANT_VERSION` = `1.2.0` з фази 4: облікові дані — feature `credentials`); №12 уже порівнює | D2, ТЗ |
| 9 | Хто керує обліковими даними | `ADMIN` — у Face (Settings → **Robot credentials**); `DEVELOPER` — лише бачить назву й логін у випадайці Studio; пароль не повертається ніколи. Права `CREDENTIAL_VIEW` (адмін, розробник), `CREDENTIAL_MANAGE` (адмін) | 03, D20 |
| 10 | Шифрування | «конвертом» на ключі організації (F3, `OrganizationSecrets`) | наявний фундамент |
| 11 | Видалення облікових даних, що використовуються | 409 зі списком роботів і версій (`GET /credentials/{id}/usage`) | 14: «видалення того, що використовується, треба притримувати» |
| 12 | Доставка паролю агенту | при відправці запуску оркестратор розшифровує використані облікові дані й кладе в `execution/assign` (`credentials`, по `wss`); облікових даних немає — запуск `BLOCKED` | D20, D48 |
| 13 | Маскування | Assistant замінює значення всіх отриманих облікових даних на `***` у **кожному** рядку логу й у помилці | D20: «за жодних обставин» |
| 14 | Аудит і сповіщення | `CREDENTIAL_CREATED` / `UPDATED` / `SECRET_CHANGED` / `DELETED` в аудит; сповіщення адмінам (`INFO`) | D41, правило сповіщень |
| 15 | Блокування облікових даних між запусками (D69) | **фаза 5** (так у roadmap) | — |

## Живі прогони (E8, 2026-11-07)

Стек dev (Orchester API / worker / scheduler, Studio-back API / worker, Keycloak,
RabbitMQ, Postgres); міграцію `a8d2c6e4f915` накочено на dev-БД. Браузер — headless
Chrome з окремим профілем (CDP), Assistant — з розробки, потім зібраний `.exe` 1.2.0.
Облікові дані «Buh test login» (`buh`) створено адміном через `POST /credentials`.

| Що | Результат |
|----|-----------|
| Новий робот → елементи (4) через вкладку «Advanced (JSON)» (у житті — Inspector) → **кроки лише кліками в редакторі**: Attach window, Type text (логін — облікові дані, частина «Login»), Type text (пароль — облікові дані, «Password»), Click, Log | у JSON — `{"credential": id, "part": ...}`, а не текст; перевірка: 0 помилок, 4 попередження «одна стратегія», `Needs Assistant 1.2.0` |
| Додано `Log` без повідомлення | «1 ERRORS», `s6 «Message» is required` — під полем і в панелі; **Save і Run вимкнені**; після видалення кроку — знову активні |
| Run (dev Assistant) | `COMPLETED`, 5 кроків; тестове вікно отримало `LOGIN buh <пароль>`; пароля немає в жодному лозі (Assistant, Orchester API / worker, Studio-back) |
| Run (зібраний `.exe` 1.2.0) | те саме — `COMPLETED`, `LOGIN buh <пароль>`, у логах exe пароля немає |
| `DELETE /credentials/{id}`, коли ним користуються | 409 «used by RBT-23, RBT-24, RBT-25…»; `usage` — 3 версії |
| Desktop UIA-тести з новими полями вікна | 246 passed (`TEKRA_UIA_TESTS=1`) |

Знайдено й виправлено під час прогону: відповідь перевірки на **попередній**
сценарій могла з'явитися в панелі, поки триває debounce нової зміни (запит, що
летів, не скасовувався до кінця debounce) — тепер кожна зміна скасовує запит у
дорозі (`robot-detail`: `switchMap` → `timer` → `validate`).
