# Tekra workspace — правила для розробників і AI-агентів

> **Це канонічна версія.** Файл живе в репозиторії `Tekra_Documentation`.
> У корені воркспейсу (`d:/tekra/AGENTS.md`) лежить короткий вказівник на цей
> файл — правити треба **тут**, інакше зміни не потраплять під git.

Цей файл — **спільна угода** для всіх, хто змінює код у `d:\tekra`: людей, **Cursor** і **Claude Code**. Його мета — стабільний контекст, передбачувані зміни і менше сюрпризів між сесіями агентів.

## 1. Карта репозиторію

| Проєкт | Призначення | Технології (орієнтир) |
|--------|-------------|------------------------|
| `Tekra-Orchester/` | API та серверна логіка | Python, FastAPI, Redis, Alembic, WebSocket |
| `Tekra-Orchester-Face/` | Веб-клієнт до API | Angular 18+, TypeScript |
| `Tekra-Desktop/` | Десктоп-клієнт | Python, PyQt, WebSocket-клієнт |

### Словник у розмовах (що мають на увазі агенти)

У чатах і задачах команди ці слова **завжди** відповідають таким каталогам (регістр не важливий):

| Як кажуть | Каталог на диску |
|-----------|------------------|
| **десктоп**, desktop | `Tekra-Desktop/` |
| **оркестратор**, orchestrator | `Tekra-Orchester/` |
| **фронтенд**, frontend, **оркестратор фейс**, orchestrator face, **фейс**, face, **Angular**, angular | `Tekra-Orchester-Face/` |

Якщо формулювання двозначне — уточнити в людини перед зміною коду.

Детальніше про шляхи та команди: [`README.md`](README.md).

## 2. Порядок читання на початку задачі (обов’язково)

1. **Цей файл** (`AGENTS.md`) — загальні правила workspace.
2. **Документація конкретного проєкту**: `<Проєкт>/docs/` (зокрема `FOR-AGENTS.md`, коли з’являться детальніші нотатки).
3. **README** відповідного проєкту (якщо є).
4. Лише після цього — вибіркове читання коду в межах задачі.

Якщо зміни торкаються кількох проєктів — явно перелічити це в описі задачі / PR.

## 3. Принципи роботи (люди й агенти)

- **Мінімальний diff**: змінювати лише те, що потрібно для задачі; без «поки ми тут»-рефакторингів у чужих модулях.
- **Спочатку прочитати контекст**: суміжні файли, існуючі патерни іменування, імпорти, обробку помилок — копіювати стиль проєкту. Для **оркестратора** та **десктопа** деталізовано в їхніх `docs/FOR-AGENTS.md` (узгодженість з Pydantic, шарами, PyQt тощо).
- **Одна задача — один змістовний результат**: якщо scope роздувся, зупинитись і узгодити з людиною.
- **Доводити фічу до ВИДИМОГО результату, а не до endpoint/поля.** Для задачі «покажи X у Y» простежити ланцюг наскрізь: **компонент/елемент UI → який селектор/сервіс/API читає → який backend-endpoint → чи повертає він це поле**. Поле має бути саме в тому джерелі, що споживає цільовий елемент, а не в «сусідньому схожому» endpoint (інакше UI лишиться порожнім, хоча дані «є»). «Однаково в A і B» — пройти **обидва** ланцюги окремо: симетрія бекенду ≠ симетрія відображення. Зелений lint / typecheck / build **≠** «працює» — вони не ловлять wiring через не той endpoint. Довести результат (відкрити екран і глянути елемент або хоча б grep-довести, що рендер читає поле звідки треба).
- **Крос-проєктні зміни**: коротко задокументувати в PR (що змінилось і чому в кожному репо).
- **Мова комітів і PR**: узгодити в команді; за замовчуванням — **англійська** для повідомлень у git (зручніше для змішаних команд і пошуку в історії).

## 4. Робота за UI-макетом (1:1)

**Жорстке постійне правило для всіх агентів і людей** у цьому workspace.

Якщо для задачі надано **дизайн-макет** (Figma або інше джерело), UI-верстка та компоненти робляться **1:1 з макетом**: склад і порядок елементів, написання текстів, відступи, кольори, типографіка, стани (active / hover / focus / disabled), іконки. Жодних «приблизно», «близько до» чи «своїх покращень».

**Без явного дозволу замовника не можна:**
- змінювати порядок або назви пунктів навігації / списків;
- перекладати, скорочувати чи переставляти слова у текстах;
- замінювати іконки на «схожі» (з іншої бібліотеки тощо);
- додавати елементи, яких немає на макеті;
- прибирати елементи, які є на макеті;
- варіювати кольори активного / hover-стану, фон, бордери, радіуси.

**Розбіжності:**
- між макетом і чинним кодом → старе вважається **застарілим**, код переробляється під макет;
- усередині макета (різні фрейми показують одне й те ж по-різному, бракує стану) → **зупинитись і запитати**, не вгадувати.

**Що означає «надано макет»:** посилання на Figma-фрейм (із `node-id`), скріншот зі вказівкою «робимо як тут», або файл у `<project>/docs/`. Усне «такий собі» макетом не вважається — питати уточнення.

## 5. Live backend integration (жорстке правило)

**Tekra-Orchester-Face працює у зв'язці з реальним `Tekra-Orchester` (live backend).** Це не прототип з моками — backend піднятий, фронт активно використовує його endpoints.

**Без явного дозволу замовника заборонено:**
- залишати в проді **mock-respons-и** в коді фронту (`return of(fakeData)`, `setTimeout(() => …)` як заміна HTTP-виклику);
- хардкодити дані, які мають приходити з API (профілі, списки, налаштування) — без явного маркера `// TODO: replace with API call to <endpoint>`;
- винаходити «зручний» формат payload, що не збігається з тим, що приймає / повертає backend;
- лиш «маскувати» помилки бекенду (приховати 4xx/5xx) — їх потрібно показувати користувачу.

**Якщо для нової фічі потрібен endpoint, якого ще немає на бекенді:**
1. **Зупинитись і узгодити** — визначити форму request/response і назву endpoint з замовником.
2. Реалізувати на бекенді (`Tekra-Orchester`) **спочатку**, потім підключати з фронту.
3. Не писати фронт «наосліп» з вигаданим контрактом.

**Винятки (де hardcoded даних поки що дозволено):**
- Чорнові verstki сторінок під дизайн-макет, поки конкретний endpoint ще не виділений — позначати в коді `// TODO(api): <…>` і дублювати в `Tekra-Orchester-Face/docs/FOR-AGENTS.md` чи в memory.
- UI-стани без серверної семантики (наприклад, локально розкритий menu, поточний tab) — це нормальний клієнтський стан.

**Поточні робочі endpoints, що використовуються:** див. [`Tekra-Orchester-Face/docs/FOR-AGENTS.md`](https://github.com/tekra007/Tekra-Orchester-Face/blob/main/docs/FOR-AGENTS.md) та `Tekra-Orchester` swagger (`/docs`). Перед новою фічею перевіряти що endpoint справді існує та реалізований.

## 5a. Admin notifications (Tekra-Orchester)

Будь-яка нова фіча, що змінює стан, видимий адмінам (юзери, ліцензії, роботи,
безпека, фонові задачі) **зобов'язана** створити запис у `admin_notifications`
через `AdminNotificationService.safe_notify_organization(...)` (fan-out усім
адмінам org) або `safe_notify_admin(...)` (тільки актору — для його власних
безпекових подій). Helper'и fail-safe — нотифікація **ніколи** не валить
основний потік.

Деталі (типи, місце виклику, що НЕ нотифікувати):
[`Tekra-Orchester/docs/FOR-AGENTS.md`](https://github.com/tekra007/Tekra-Orchester/blob/main/docs/FOR-AGENTS.md) →
розділ «Admin notifications».

## 6. Безпека та конфігурація

- Не комітити **секрети**, токени, паролі, приватні ключі, реальні `.env`. У репозиторії лише **приклади** на кшталт `.env.sample`.
- Не підставляти реальні облікові дані в приклади в документації.

## 7. База даних і міграції (Tekra-Orchester)

- **Не генерувати й не застосовувати міграції Alembic автоматично** без явного запиту людини.
- Додавання полів у моделі: зміни в коді/схемах узгоджувати з людиною; **створення міграції** — відповідальність людини (або окремо узгоджений крок).
- Не видаляти наявні поля метрик / колонок без явного запиту.

## 8. Тестування й якість

- Після змін у відповідному проєкті варто прогнати релевантні перевірки (наприклад, `pytest` у Orchester, `ng test` / лінтер у Face — коли з’являться у `docs` конкретні команди).
- Не «ламати» існуючі публічні контракти API без оновлення клієнтів і нотатки в PR.

## 9. Два AI-агенти (Cursor і Claude Code)

- **Єдине джерело правди для workspace**: цей `AGENTS.md` + репозиторій `Tekra_Documentation/` + `docs/` у кожному проєкті.
- Уникати **паралельного редагування одних і тих самих файлів** двома агентами; якщо так вийшло — вирівняти зміни через людину / rebase.
- Після великих рішень (архітектура, контракт API, неочевидні обмеження) — **короткий запис** у `<Проєкт>/docs/` (наприклад, окремий файл `DECISIONS.md` або розділ у `FOR-AGENTS.md`), щоб наступна сесія не вигадувала все з нуля.

## 10. Документація для агентів

- **Загальне** (це все): корінь `tekra` — `AGENTS.md`; крос-репозиторійне проєктування — `Tekra_Documentation/` (окремий git-репозиторій).
- **По проєкту**: `<Проєкт>/docs/` — домовленості саме для FastAPI / Angular / Desktop (команди запуску, шари архітектури, що чіпати обережно).

Якщо щось застаріло в `docs` — краще виправити нотатку, ніж покладатись на «пам’ять» агента з минулої сесії.

## 11. Оновлення цих правил

Зміни в `AGENTS.md` узгоджувати так само, як код: зрозуміле повідомлення коміту, за потреби — короткий опис у PR. Правила мають залишатись **короткими й виконуваними**; деталі стеку виносити в `<Проєкт>/docs/`.
